TL;DR

🧠 The mental model in one line: writing CUDA is not about how to compute — it's about how data moves.

A GPU has compute to spare; the bottleneck is almost always memory. The classic beginner failure is spending all the time on syntax (<<<>>>, cudaMalloc), producing a kernel that works but is slower than the CPU, and then giving up. The time actually belongs in chapter 3, the memory hierarchy.

Suggested order (which is this article's outline): first kernel → mental model → execution model → memory hierarchy → warps and reduction → which bound you're in → real kernels.

The one thing that matters most: do not skip chapter 3. 90% of performance problems are memory problems, and every other chapter is in service of it.

★ This assumes you already have a working CUDA environment (an NVIDIA GPU plus the CUDA Toolkit, with nvcc --version responding). Save every example as a .cu file and compile it with nvcc.

0 · Your first kernel — what a CUDA program looks like

The skeleton of a CUDA program

Every CUDA program is the same four steps: allocate on the host (CPU) → copy to the device (GPU) → launch a kernel → copy the result back. Every chapter after this is just about writing that middle step better.

Save this as add.cu:

#include <stdio.h>

__global__ void add(const float* a, const float* b, float* c, int n){
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];   // never skip the bounds check: threads almost always > n
}

int main(){
  int n = 1<<20;  size_t bytes = n * sizeof(float);
  float *ha = (float*)malloc(bytes), *hb = (float*)malloc(bytes), *hc = (float*)malloc(bytes);
  for (int i=0;i<n;i++){ ha[i]=1.0f; hb[i]=2.0f; }

  float *da,*db,*dc;
  cudaMalloc(&da,bytes); cudaMalloc(&db,bytes); cudaMalloc(&dc,bytes);
  cudaMemcpy(da,ha,bytes,cudaMemcpyHostToDevice);
  cudaMemcpy(db,hb,bytes,cudaMemcpyHostToDevice);

  add<<<(n+255)/256, 256>>>(da,db,dc,n);   // <<<how many blocks, threads per block>>>
  cudaMemcpy(hc,dc,bytes,cudaMemcpyDeviceToHost);

  printf("c[0]=%f  c[n-1]=%f\n", hc[0], hc[n-1]);   // both should be 3.0
  return 0;
}
nvcc -O2 add.cu -o add && ./add

★ Printing c[0]=3.000000 means it worked. Those 20 lines already contain the entire CUDA skeleton — everything that follows just rewrites the add kernel itself.

Prerequisite: only C pointers

The amount of C you need is surprisingly small: pointers, malloc/free, arrays and address arithmetic. That's it. You do not need C++ (templates, STL, RAII are all irrelevant at first), and you do not need operating systems or compiler knowledge.

But you genuinely can't skip this part. CUDA moves memory by hand from start to finish. If pointers are shaky, chapter 2's cudaMemcpy becomes a magic incantation you copy without understanding, and chapter 3's shared memory will stop you dead. If your background is mostly Python or JavaScript, spend 2–3 days on pointers first — it's the highest-return few days on the whole path.

1 · Mental model — why GPUs are fast, and why they often aren't

Where the speed comes from

A CPU is designed to minimise the latency of one task: huge caches, branch prediction, out-of-order execution — all of it spent making a single instruction stream run as fast as possible. A GPU inverts that. It spends those transistors on more cores, aiming for total throughput.

The consequence is simple: a GPU only pays off when you have a lot of independent data all doing the same thing. Adding 10 numbers? The CPU wins outright — just moving the data across PCIe loses the race. Adding 100 million numbers? The GPU is an order of magnitude ahead.

Three numbers to memorise on day one

Using an NVIDIA T4 as the example (other cards have different numbers, but the ratio holds):

ItemNumberWhat it means
Memory bandwidth~320 GB/sHow much data you can pull from VRAM per second — usually your actual ceiling
FP32 compute~8.1 TFLOPSHow many floating-point operations per second
Ratio~100 : 1For every float fetched from memory, the GPU has time for ~100 operations

That last row is the single most important line in this article. It means that if your kernel does only one or two operations per float loaded — vector add is exactly this — then 99% of your compute sits idle and you are memory-bound. The only way to optimise such a kernel is to move less data, or move it more cleverly. Making the arithmetic faster does nothing.

The vast majority of real kernels (elementwise ops, softmax, layernorm, much of attention) are memory-bound. That's why chapter 3 is the one that matters.

2 · Execution model — threads, blocks, grids

There's really only one idea here

When you write a CUDA kernel you write what one thread does, and the GPU runs a few million copies of it at once. So the first thing every thread does is ask who it is:

int i = blockIdx.x * blockDim.x + threadIdx.x;
//    ↑ which block am I in  ↑ threads per block  ↑ my index inside the block

That line is CUDA's loop counter. Where a CPU writes for(i=0;i<n;i++), a GPU flattens the loop and hands each i to its own thread.

Three things people trip over

The bounds check is not optional
Block count rounds up ((n+255)/256), so you almost always launch more threads than n. Without if (i < n) you write out of bounds — and it won't necessarily crash. It may just quietly corrupt other memory.
Kernel launches are asynchronous
add<<<…>>>() returns immediately and the CPU keeps going. To time anything you need cudaDeviceSynchronize() first, otherwise you measure how long it took to queue the work and get an absurd 0.01 ms.
CUDA errors are silent
A failing kernel throws nothing — it just sets an error flag. Add a checking macro on day one, or you will spend hours debugging a kernel that never ran.
// Paste this in from day one. It saves more time than you'd guess.
#define CUDA_CHECK(x) do { cudaError_t e = (x); \
  if (e != cudaSuccess) { \
    fprintf(stderr, "CUDA error %s at %s:%d\n", cudaGetErrorString(e), __FILE__, __LINE__); \
    exit(1); } } while(0)

CUDA_CHECK(cudaMalloc(&da, bytes));
add<<<grid, block>>>(da, db, dc, n);
CUDA_CHECK(cudaGetLastError());        // catches launch failures (e.g. block too large)
CUDA_CHECK(cudaDeviceSynchronize());   // catches runtime failures (e.g. out-of-bounds access)

Choosing a block size

Don't overthink it: 256. It's a multiple of the warp size (32), works nearly everywhere, and is the community default. Once you can read which bound you're in (chapter 5), come back and try 128 or 512. Tuning it before then is wasted effort.

3 · Memory hierarchy — the center of gravity ★

If you only have time for one chapter, make it this one.

As established: compute-to-bandwidth is 100:1. So all of CUDA optimisation reduces to two moves — ① make every fetch a full fetch (coalescing), and ② reuse what you fetched before throwing it away (shared memory tiling).

① Coalescing — make every fetch a full fetch

The hardware doesn't read 4 bytes at a time — it reads a whole segment (typically 32 or 128 bytes). If the 32 threads of a warp happen to want contiguous addresses, the hardware merges them into a handful of transactions and bandwidth is fully used. If they jump around, each thread needs its own transaction, and each of those drags back a whole segment of which only 4 bytes are wanted.

In practice there's one rule: adjacent threads should read adjacent addresses. That means a[i] where i contains threadIdx.x — not a[i * stride].

The canonical illustration is matrix transpose: reads are contiguous but writes are strided (or the other way round), so no matter how you write it half of it is bad — unless you route through shared memory. Which brings us to the second move.

② Shared memory tiling — reuse what you fetched

Shared memory is a cache you manage yourself: shared by all threads in a block, roughly two orders of magnitude faster, but only tens of KB. The usage pattern is always the same:

// each block computes one 16×16 tile of the output matrix
__global__ void matmul_tiled(const float* A, const float* B, float* C, int N){
  __shared__ float As[16][16], Bs[16][16];
  int ty = threadIdx.y, tx = threadIdx.x;
  int row = blockIdx.y * 16 + ty, col = blockIdx.x * 16 + tx;
  float acc = 0.0f;

  for (int t = 0; t < N/16; ++t) {
    As[ty][tx] = A[row * N + (t*16 + tx)];      // ① cooperatively load a tile into shared
    Bs[ty][tx] = B[(t*16 + ty) * N + col];
    __syncthreads();                            // ② wait for everyone before reading

    for (int k = 0; k < 16; ++k)                 // ③ this tile gets used 16 times, not once
      acc += As[ty][k] * Bs[k][tx];
    __syncthreads();                            // ④ wait for everyone before overwriting
  }
  C[row * N + col] = acc;
}

Step ③ is the whole trick. The naive version fetches two numbers from global memory per multiply-add; the tiled version loads once into shared and then uses it 16 times. Traffic drops by 16×. That's the entire secret.

★ Both __syncthreads() calls are required, and dropping either produces the worst kind of bug: correct on small matrices, occasionally wrong on large ones. The fourth is the one people forget — without it, fast threads overwrite the tile while slower ones are still reading it.

The other trap is bank conflicts: shared memory is split across 32 banks, and if several threads in a warp hit different addresses in the same bank, the accesses serialise. Transpose-shaped access patterns are the usual offender, and the classic fix is to declare the array as As[16][17] — one column of padding to knock the alignment out of phase. It looks like a hack; it is genuinely standard practice.

Tile edges of 16 or 32 are both common, and the choice comes down to shared memory capacity and register use per thread. Those two squeeze each other: a bigger tile means more reuse, but fewer blocks fit on an SM at once.

4 · Warps and reduction — from writing it to writing it well

The warp is the real unit of execution

Saying "each thread runs independently" was a simplification. The GPU actually schedules in units of a warp — 32 threads — and those 32 share a single instruction pointer. They are always executing the same line of code.

Which gives you warp divergence:

if (threadIdx.x % 2 == 0) do_A();   // half the warp goes here
else                      do_B();   // the other half goes there
// → hardware must run A for everyone (B's half idle), then B (A's half idle)
// → this warp costs A + B: half your throughput, gone

Note that a bounds check like if (i < n) is essentially free — only the final warp diverges, which is negligible. What you actually want to avoid is branching on thread id inside a warp.

Reduction: turning n numbers into one

This is the classic GPU exercise precisely because it fights the parallel model — every thread wants to write the same result. The standard answer is a halving tree:

// Stage A: halving tree within a block, through shared memory
for (int s = blockDim.x / 2; s > 32; s >>= 1) {
  if (tid < s) sdata[tid] += sdata[tid + s];
  __syncthreads();
}
// Stage B: once 32 are left they're one warp, so shuffle registers directly —
//          no shared memory and no __syncthreads() needed at all
if (tid < 32) {
  float v = sdata[tid] + sdata[tid + 32];
  for (int off = 16; off > 0; off >>= 1)
    v += __shfl_down_sync(0xffffffff, v, off);   // 0xffffffff = all 32 participate
  if (tid == 0) out[blockIdx.x] = v;
}

NVIDIA has a classic deck, Optimizing Parallel Reduction in CUDA, that takes this kernel from naive to near-bandwidth-limit across 7 versions and 30× of speedup. Every trick it demonstrates — avoiding divergence, avoiding bank conflicts, unrolling the last warp, having each thread handle several elements up front — is a general technique, not something specific to reduction.

★ When you sum a large number of floats, the GPU result will not exactly match a serial CPU one, and that's not a bug — floating-point addition isn't associative, so a different summation order gives a different answer. It's an inherent property of summing in parallel.

5 · Which bound you're in — where to optimise

Once you can write kernels, the next question is which direction to change them. CUDA's optimisation techniques trade against each other — saving memory traffic usually costs arithmetic, and vice versa. Pick the wrong direction and you don't just waste effort, you make the kernel slower.

The only rule you need: roofline

Ask one question: which hits the ceiling first, memory throughput or compute throughput? NVIDIA's nsys (a whole-program timeline) and ncu (per-kernel detail) hand you both percentages directly. Three cases, three completely different directions:

Memory near 100%, compute low
Memory-bound. This is the normal case. Optimise toward moving less data: coalescing, shared memory reuse, kernel fusion (merge several elementwise kernels so data isn't shuttled back and forth).
→ Faster arithmetic buys nothing
Compute near 100%, memory low
Compute-bound. Rarer — well-optimised matmul eventually gets here. Optimise toward computing less or computing cheaper: lower precision, tensor cores, removing redundant work.
→ Faster data movement buys nothing
Both low
Latency-bound. The GPU is waiting. Usually low occupancy (too many registers per thread, oversized shared memory), heavy divergence, or too much synchronisation.
→ Now look at the occupancy figure

★ High occupancy does not mean fast. This is where beginners get misled most often. Occupancy only measures your ability to hide latency, and plenty of world-class kernels deliberately run at low occupancy to get more registers. Read memory and compute throughput first; occupancy only matters when both are low.

A whole-program timeline often reveals something more fundamental: the bottleneck isn't the kernel at all, it's cudaMemcpy. No amount of kernel tuning helps there — the fix is fewer host-device round trips, or streams so transfers overlap with compute.

6 · Real kernels — write things people actually use

The first five chapters are common ground. Here you pick a direction. The order below assumes your goal is AI / LLM inference, currently where CUDA skills are most in demand. If you're aiming at graphics or scientific computing, swap out this chapter's targets — the first five are unchanged.

OrderKernelWhat's new in itDifficulty
1SoftmaxTwo passes (max, then sum), numerical stability (subtract the max first), row-wise reductionMedium
2LayerNormMean and variance in one pass, Welford's algorithm, kernel fusionMedium
3Online softmaxSoftmax in a single pass — the core trick behind flash attentionMed-high
4Simplified flash attentionAll of the above together: tiling plus online softmax, never materialising the N×N matrixHard

These are order-dependent — 3 is a prerequisite for 4 in particular. Once you've done 4 you'll genuinely understand why flash attention saves so much memory: it doesn't save compute, it saves data movement, which is exactly the 100:1 from chapter 1 paying off.

When you're allowed to use libraries

Once you've hand-written matmul, you should switch to cuBLAS. Your version will reach maybe 50–70% of it, and the remaining gap is a decade of hand-tuning that isn't worth chasing from scratch. The value of writing it yourself was learning why, not replacing the library.

Same logic for Triton (GPU kernels in Python) — picking it up now will feel effortless, because you already know what it's automating. People who start with Triton tend to hit a wall the moment they need manual control over memory.

What not to do yet

Don't start with Triton or other abstractions
Triton, CuPy and Numba earn their keep by handling the memory hierarchy for you. Start there and you skip chapter 3 — the most important chapter here — then get stuck the first time you need manual control.
Learn it after chapter 6; it'll be much faster
Don't reach for cuBLAS / cuDNN early
They're for saving effort at the end, not for learning. Calling a library on day one teaches you nothing.
Use them once you've hand-written matmul
Don't read the Programming Guide cover to cover
It's a reference manual, not a course, and it covers a great deal you won't touch for years (dynamic parallelism, graphics interop, multi-GPU…). Reading it linearly just makes you quit around page 20.
Consult it when you have a specific question
Don't optimise on instinct
"I used shared memory, so it should be faster" is wrong more often than you'd expect. An oversized tile, bank conflicts, or crushed occupancy all make the "optimisation" slower. Work out the direction from chapter 5 first.
Wrong direction, no amount of tuning helps
Don't agonise over block size
Use 256. Tuning it before you can profile is guessing at a parameter with no feedback signal.
Come back to it after chapter 5
