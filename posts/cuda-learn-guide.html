CUDA．從零開始的 GPU 程式學習路線

假設你手上已經有能跑 CUDA 的環境，這篇只講怎麼寫——先學什麼、後學什麼，每個概念都配圖解與可直接編譯的範例。
從一支 20 行的 kernel 開始，到看懂為什麼 flash attention 省下的是記憶體搬運，而不是算力。
對象:寫過程式、沒碰過 GPU 前置:C 的指標 環境:已裝好 CUDA Toolkit 整理日:2026-08-03

TL;DR

🧠 一句話心智模型：寫 CUDA 不是在寫「怎麼算」，是在寫「資料怎麼搬」。

GPU 的算力遠遠過剩，瓶頸幾乎永遠在記憶體。新手最常見的失敗是把時間全花在語法（<<<>>>、cudaMalloc）上，然後寫出一個「會動但比 CPU 還慢」的 kernel，卡住、放棄。真正該花時間的是第 3 章的記憶體階層。

建議順序（也就是本篇章節）：第一支 kernel → 心智模型 → 執行模型 → 記憶體階層 → warp 與 reduction → 瓶頸判讀 → 實戰 kernel。

最重要的一件事：不要跳過第 3 章。90% 的效能問題是記憶體問題，其他章節都在服務它。

★ 本篇假設你已經有能跑 CUDA 的環境（NVIDIA 顯卡 + CUDA Toolkit，nvcc --version 有反應）。所有範例存成 .cu 檔，用 nvcc 編譯就能跑。

0 · 第一支 kernel — CUDA 程式長什麼樣

CUDA 程式的骨架

一支 CUDA 程式永遠是同樣四步：在 host（CPU）配記憶體 → 搬到 device（GPU）→ 啟動 kernel → 把結果搬回來。後面每一章都只是在把中間那一步寫得更好。

存成 add.cu：

#include <stdio.h>

__global__ void add(const float* a, const float* b, float* c, int n){
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) c[i] = a[i] + b[i];   // 邊界檢查不能省：thread 總數幾乎一定 > n
}

int main(){
  int n = 1<<20;  size_t bytes = n * sizeof(float);
  float *ha = (float*)malloc(bytes), *hb = (float*)malloc(bytes), *hc = (float*)malloc(bytes);
  for (int i=0;i<n;i++){ ha[i]=1.0f; hb[i]=2.0f; }

  float *da,*db,*dc;
  cudaMalloc(&da,bytes); cudaMalloc(&db,bytes); cudaMalloc(&dc,bytes);
  cudaMemcpy(da,ha,bytes,cudaMemcpyHostToDevice);
  cudaMemcpy(db,hb,bytes,cudaMemcpyHostToDevice);

  add<<<(n+255)/256, 256>>>(da,db,dc,n);   // <<<幾個 block, 每 block 幾個 thread>>>
  cudaMemcpy(hc,dc,bytes,cudaMemcpyDeviceToHost);

  printf("c[0]=%f  c[n-1]=%f\n", hc[0], hc[n-1]);   // 應該都是 3.0
  return 0;
}
nvcc -O2 add.cu -o add && ./add

★ 印出 c[0]=3.000000 就對了。這 20 行裡已經有 CUDA 的全部骨架，剩下的章節都只是在改寫 add 這個 kernel 本身。

前置知識：只要 C 的指標

你需要的 C 少得出乎意料：指標、malloc/free、陣列與位址運算。就這些。不需要 C++（模板、STL、RAII 一開始都用不到）、不需要作業系統或編譯器知識。

但這一塊真的不能跳。CUDA 全程在手動搬記憶體，指標不熟的話，第 2 章的 cudaMemcpy 就會變成「照抄咒語」，第 3 章的 shared memory 一定卡死。如果你主要背景是 Python 或 JavaScript，先花 2–3 天補指標，這是整條路線投報率最高的兩三天。

1 · 心智模型 — GPU 為什麼快，又為什麼常常不快

GPU 快在哪

CPU 的設計目標是降低單一任務的延遲：大量快取、分支預測、亂序執行，全部拿來讓一條指令流跑得越快越好。GPU 反過來，它把那些電晶體通通拿去多塞核心，目標是拉高總吞吐量。

結論很簡單：GPU 只有在你有大量彼此獨立、而且做同一件事的資料時才划算。10 個元素相加？CPU 完勝，光是把資料搬過 PCIe 就輸了。1 億個元素相加？GPU 快一個數量級。

三個從第一天就要記住的數字

以 NVIDIA T4 為例（其他卡數字不同，但比例關係一樣）：

項目數字意思
記憶體頻寬約 320 GB/s每秒能從顯存搬多少資料——這通常就是你的天花板
FP32 算力約 8.1 TFLOPS每秒能做多少次浮點運算
兩者比值約 100 : 1每從記憶體搬 1 個 float，GPU 就有時間做約 100 次運算

最後那一列是整篇文章最重要的一句話。它的意思是：如果你的 kernel 每讀一個 float 只做一兩次運算（vector add 就是這種），那你 99% 的算力是閒置的，你被記憶體綁住了。這種 kernel 叫 memory-bound，優化它的唯一方向是「少搬、搬得更聰明」，不是「算得更快」。

絕大多數真實 kernel（elementwise、softmax、layernorm、attention 的一部分）都是 memory-bound。這就是為什麼第 3 章最重要。

2 · 執行模型 — thread、block、grid

你只需要理解一件事

寫 CUDA kernel 時，你寫的是「一個 thread 要做什麼」，然後 GPU 幫你把它複製幾百萬份同時跑。所以每個 thread 的第一件事永遠是問自己「我是誰」：

int i = blockIdx.x * blockDim.x + threadIdx.x;
//    ↑ 我在第幾個 block   ↑ 每 block 幾個 thread  ↑ 我在 block 內第幾個

這一行就是 CUDA 的「for 迴圈索引」。CPU 寫 for(i=0;i<n;i++)，GPU 就是把迴圈攤平，每個 i 給一個 thread。

三個容易踩的地方

邊界檢查不能省
block 數要無條件進位（(n+255)/256），所以 thread 總數幾乎一定大於 n。少了 if (i < n) 就是越界寫入，而且不一定會當——它可能只是靜靜地污染別的記憶體。
kernel 啟動是非同步的
add<<<…>>>() 會立刻返回，CPU 繼續往下跑。要量時間得先 cudaDeviceSynchronize()，否則你量到的是「發送指令」的時間，會得到荒謬的 0.01 ms。
CUDA 錯誤是沉默的
kernel 出錯不會丟例外，只會設一個 error flag。從第一天就包一個檢查巨集，不然你會花好幾小時 debug 一個早就失敗的 kernel。
// 從第一天就貼上這個。省下的時間比你想像的多。
#define CUDA_CHECK(x) do { cudaError_t e = (x); \
  if (e != cudaSuccess) { \
    fprintf(stderr, "CUDA error %s at %s:%d\n", cudaGetErrorString(e), __FILE__, __LINE__); \
    exit(1); } } while(0)

CUDA_CHECK(cudaMalloc(&da, bytes));
add<<<grid, block>>>(da, db, dc, n);
CUDA_CHECK(cudaGetLastError());        // 抓「啟動失敗」（例如 block 開太大）
CUDA_CHECK(cudaDeviceSynchronize());   // 抓「執行中失敗」（例如越界存取）

block size 怎麼選

先別想太多：256。它是 warp（32）的倍數、適用於幾乎所有情境、也是社群的預設答案。等你到第 5 章看得懂瓶頸了，再回頭調 128 / 512——在那之前調它是浪費時間。

3 · 記憶體階層 — 整條路線的重心 ★

如果你只有時間學一章，學這章。

前面說過：算力對頻寬是 100:1。所以 CUDA 優化的全部內容，其實就是兩個動作——①讓每次搬運都搬滿（coalescing）、②搬過來的資料多用幾次再丟（shared memory tiling）。

① Coalescing — 讓每次搬運都搬滿

硬體讀顯存時不是一次讀 4 bytes，是一次讀一整段（典型 32 或 128 bytes）。同一個 warp 的 32 個 thread 如果剛好讀的是連續位址，硬體會把它們併成極少數幾次交易，效率拉滿；如果跳著讀，每個 thread 都得單獨發一次交易，而且每次搬回來的一整段裡只有 4 bytes 有用。

實務上的規則只有一條：讓相鄰的 thread 讀相鄰的位址。也就是 a[i]，其中 i 含有 threadIdx.x；不要寫成 a[i * stride]。

這件事最經典的例子是矩陣轉置：讀的時候是連續的，寫的時候變成跨步的（或反過來），所以無論怎麼寫都有一半是壞的——除非你用 shared memory 中轉。這就接到第二個動作。

② Shared memory tiling — 搬過來多用幾次

Shared memory 是你自己管理的快取：同一個 block 的 thread 共用，快上約兩個數量級，但只有幾十 KB。用法固定成一個套路：

// 每個 block 負責輸出矩陣的一塊 16×16 tile
__global__ void matmul_tiled(const float* A, const float* B, float* C, int N){
  __shared__ float As[16][16], Bs[16][16];
  int ty = threadIdx.y, tx = threadIdx.x;
  int row = blockIdx.y * 16 + ty, col = blockIdx.x * 16 + tx;
  float acc = 0.0f;

  for (int t = 0; t < N/16; ++t) {
    As[ty][tx] = A[row * N + (t*16 + tx)];      // ① 合作搬一塊進 shared
    Bs[ty][tx] = B[(t*16 + ty) * N + col];
    __syncthreads();                            // ② 等全員搬完才能讀

    for (int k = 0; k < 16; ++k)                 // ③ 這塊資料被用 16 次，不是 1 次
      acc += As[ty][k] * Bs[k][tx];
    __syncthreads();                            // ④ 等全員算完才能覆蓋下一塊
  }
  C[row * N + col] = acc;
}

關鍵在③：naive 版本每算一次乘加就要去 global memory 讀兩個數；tiled 版本搬一次進 shared 之後用 16 次。搬運量直接砍成 1/16，這就是全部的祕密。

★ 兩個 __syncthreads() 少一個都會錯，而且是那種「小矩陣看起來對、大矩陣才偶爾錯」的錯。第 ④ 個尤其容易漏——沒有它，跑得快的 thread 會在別人還在讀舊 tile 時就覆蓋掉它。

另一個坑是 bank conflict：shared memory 分成 32 個 bank，同一個 warp 若有多個 thread 同時打到同一個 bank 的不同位址，存取會被序列化。轉置類的存取模式最容易中，經典解法是把陣列宣告成 As[16][17]——多加一欄 padding 把對齊錯開。看起來像魔法，但確實是標準做法。

tile 邊長取 16 或 32 都常見，取決於 shared memory 容量與每個 thread 的暫存器用量。這兩個數字會互相擠壓：tile 開越大、重用次數越多，但同時能塞進 SM 的 block 就越少。

4 · warp 與 reduction — 從「會寫」到「寫得好」

warp：真正的執行單位

前面說「每個 thread 獨立執行」，那是簡化說法。實際上 GPU 以 warp = 32 個 thread 為單位排程，而且這 32 個共用同一個指令指標——它們永遠在執行同一行程式碼。

這帶來一個直接後果，warp divergence：

if (threadIdx.x % 2 == 0) do_A();   // warp 內一半 thread 走這裡
else                      do_B();   // 另一半走這裡
// → 硬體只能「先全體跑 A（B 那半閒著）、再全體跑 B（A 那半閒著）」
// → 這個 warp 的耗時 = A + B，效能直接砍半

注意 if (i < n) 這種邊界檢查幾乎不算 divergence——只有最後一個 warp 會分岔，成本可忽略。真正該避免的是在 warp 內部按 thread id 分岔。

Reduction：把 n 個數變成 1 個

這是 GPU 上最經典的練習，因為它本質上跟 GPU 的並行模型衝突——所有 thread 都想寫同一個結果。標準解法是樹狀折半：

// 階段 A：block 內用 shared memory 樹狀折半
for (int s = blockDim.x / 2; s > 32; s >>= 1) {
  if (tid < s) sdata[tid] += sdata[tid + s];
  __syncthreads();
}
// 階段 B：只剩 32 個時，同一個 warp 內可以用 shuffle 直接交換 register，
//         連 shared memory 和 __syncthreads() 都不用
if (tid < 32) {
  float v = sdata[tid] + sdata[tid + 32];
  for (int off = 16; off > 0; off >>= 1)
    v += __shfl_down_sync(0xffffffff, v, off);   // 0xffffffff = 全部 32 個都參與
  if (tid == 0) out[blockIdx.x] = v;
}

NVIDIA 有一份經典簡報《Optimizing Parallel Reduction in CUDA》，把這個 kernel 從最 naive 一路優化到接近頻寬上限，總共 7 個版本、快了 30 倍以上。它示範的每一招（避免 divergence、避免 bank conflict、展開最後一個 warp、一個 thread 先處理多筆資料）都是通用手法，不只用在 reduction。

★ 用 float 累加大量數字時，GPU 的結果跟 CPU 序列版本來就不會完全一樣——浮點加法沒有結合律，相加順序不同結果就不同。這不是 bug，是並行加總的固有性質。

5 · 瓶頸判讀 — 該往哪個方向優化

寫得出來之後，下一個問題是往哪個方向改。CUDA 的優化手法互相排斥——省記憶體的做法通常會多花算力，反之亦然。選錯方向不只沒效果，還會讓 kernel 變慢。

唯一需要記住的判斷法：roofline

只問一個問題：記憶體吞吐和算力吞吐，哪個先撞到天花板？NVIDIA 的 nsys（整支程式的時間軸）與 ncu（單一 kernel 的細部指標）會直接給你這兩個百分比。三種情況，三個完全不同的方向：

記憶體接近 100%，算力很低
Memory-bound。這是常態。往「少搬資料」的方向優化：coalescing、shared memory 重用、kernel fusion（把多個 elementwise kernel 合成一個，少來回搬）。
→ 加速算術完全沒用
算力接近 100%，記憶體很低
Compute-bound。比較少見（矩陣乘法優化到後期會到）。往「算得更少或更便宜」走：降精度、用 tensor core、減少重複計算。
→ 加速搬運完全沒用
兩個都很低
Latency-bound。GPU 在空等。通常是 occupancy 太低（每 thread 用太多 register、shared memory 開太大），或 divergence 嚴重、同步太多。
→ 先看 profiler 的 occupancy 欄位

★ Occupancy 高不等於快。這是新手最常被誤導的地方。Occupancy 只是「能不能藏住延遲」的指標，很多頂尖 kernel 刻意用低 occupancy 換更多 register。先看 memory / compute 吞吐，occupancy 只在兩者都低時才看。

順帶一提，整支程式的時間軸常常會告訴你一件更根本的事：瓶頸不在 kernel，而在 cudaMemcpy。這種情況再怎麼優化 kernel 都沒用，該做的是減少 host 與 device 之間的來回，或用 stream 讓搬運跟計算重疊。

6 · 實戰 kernel — 寫真的會用到的東西

前五章是共通地基。到這裡你可以挑方向了。以下順序假設你的目標是 AI / LLM 推論——這是目前 CUDA 技能最有需求的方向。如果你的目標是圖形或科學計算，換掉這章的題目即可，前五章完全不變。

順序Kernel新學到的東西難度
1Softmax兩趟掃描（求 max、求 sum）、數值穩定性（要先減 max）、row-wise reduction中
2LayerNorm同時求 mean 與 variance、Welford 演算法、kernel fusion中
3Online Softmax單趟掃描完成 softmax——這是 flash attention 的核心技巧中高
4簡版 Flash Attention把上面全部串起來：tiling + online softmax，全程不落地 N×N 矩陣高

這四個是有順序依賴的，尤其 3 是 4 的前提。做完 4，你就真的懂為什麼 flash attention 能省下那麼多顯存了——它省的不是算力，是記憶體搬運，正好呼應第 1 章那個 100:1。

什麼時候可以開始用現成的東西

手寫完 matmul 之後，你就該用 cuBLAS 了。自己寫的 matmul 大概能到 cuBLAS 的 50–70%，剩下那段是十幾年的手工調校，不值得從頭追。手寫的價值在學會為什麼，不在取代函式庫。

同理，這時候再去看 Triton（用 Python 寫 GPU kernel）會非常順——因為你已經知道它幫你自動處理了什麼。反過來先學 Triton 的人，通常在需要手動控制記憶體時就卡住了。

現在不要做的事

不要先學 Triton 或其他抽象層
Triton、CuPy、Numba 的價值在於幫你自動處理記憶體階層。先學它們，你會跳過整篇文章最重要的第 3 章，然後在需要手動控制時徹底卡住。
學完第 6 章再回頭學，會快非常多
不要一開始就用 cuBLAS / cuDNN
它們是最後拿來省事的，不是拿來學的。一開始就呼叫函式庫，等於什麼都沒學到。
手寫過 matmul 之後就該用了
不要從頭讀官方 Programming Guide
那是參考手冊不是教材，涵蓋了大量你三年內都用不到的功能（動態並行、圖形互通、多 GPU…）。從頭讀只會讓你在第 20 頁放棄。
遇到具體問題再去查
不要憑感覺優化
「我用了 shared memory，應該比較快」——這句話錯的機率超過你想像。tile 開太大、bank conflict、occupancy 被擠掉，都會讓「優化」實際變慢。先照第 5 章判斷方向再動手。
方向錯了，改再多也沒用
不要糾結 block size
先用 256 就好。在你會用 profiler 之前調它，是拿沒有回饋訊號的參數在瞎猜。
第 5 章之後再回來調

常見的卡關點

症狀八成的原因
kernel 好像沒跑，結果全是 0沒檢查錯誤。加上 CUDA_CHECK + cudaGetLastError()，通常會看到 invalid configuration argument（block 開超過 1024）
量出來只有 0.01 ms，快得不合理忘了 cudaDeviceSynchronize()。你量到的是 CPU 發送指令的時間，kernel 還在跑
小輸入對、大輸入偶爾錯__syncthreads() 漏了，或是放在 if 裡面——block 內所有 thread 都必須執行到同一個 __syncthreads()，否則行為未定義
GPU 版比 CPU 版還慢資料量太小（搬運成本蓋過一切），或是被 cudaMemcpy 主導。用 nsys 看時間軸就一目了然
結果跟 CPU 版差在小數第 4 位不是 bug。浮點加法沒有結合律，並行的加總順序跟序列不同。用相對誤差比對，別用 ==
用了 shared memory 反而變慢bank conflict，或是 tile 太大擠壓 occupancy。用 ncu 看 shared memory 的 conflict 指標

時間規劃

假設每週投入 6–8 小時：

第 0–1 章1 週環境 + 心智模型（若要補 C 指標另加 3–5 天）
第 2 章1 週執行模型
第 3 章 ★2–3 週記憶體階層——慢慢來，這章值得
第 4 章1 週warp 與 reduction
第 5 章1 週瓶頸判讀
第 6 章持續實戰 kernel，一個一個慢慢加

總計約 6–8 週走完 0–5 章，之後就是持續累積。這個估計假設你每一章的範例都自己打過一遍——只讀不寫的話時間會短很多，但學到的東西趨近於零。CUDA 是那種只能靠手指學會的東西。
