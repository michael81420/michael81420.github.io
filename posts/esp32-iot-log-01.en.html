ESP32．IoT Learning Log 01: The Board, the Breadboard and Every Module I Tested

Step one of learning IoT: get to know the hardware on the desk. This log covers the ESP32 DevKit itself, how a breadboard connects, the electrical basics you need before wiring, and the seven modules I actually wired up over three days — each with a diagram, pinout and wiring logic. No code yet.
Source: my own ESP32 bench notes Stage: 1 / 5, the parts Compiled: 2026-09-16

TL;DR

Before wiring any module, ask three things: what voltage, is GND shared, which bus?

  • An ESP32 DevKit is a USB-serial chip + the ESP32 + 4 MB flash. Pins are 3.3V logic and not 5V-tolerant.
  • Not every pin is free: 6–11 run the flash, 34–39 are input-only, 0/2/5/12/15 are strapping pins, 1/3 are USB serial.
  • Breadboard: 5-hole columns connect, rails run lengthwise, the center gap splits the halves.
  • There are only four connection styles: GPIO (one pin per job), I2C (two wires + addresses), SPI (shared bus + chip select), UART (TX to RX).
  • Tested: on-board LED, 4-digit 7-segment display, 1602 LCD (I2C), 1.8" TFT (SPI), 4-leg button, ISD1820 recorder, 4×3 matrix keypad. Not yet: HC-SR04, buzzer.

The star: ESP32 DevKit

The ESP32 is Espressif's microcontroller: dual-core with built-in WiFi and Bluetooth (both Classic and BLE). A "DevKit" puts it on a breadboard-friendly board, adding a USB-serial chip, a 3.3V regulator, EN/BOOT buttons and an on-board LED.

Things that confused me at first

Breadboards: circuits without soldering

Inside a breadboard are metal clip strips. Knowing which holes are the same wire is most of it: holes a–e in one column are joined; f–j is another group; the red/blue rails run the full length.

  • Using the rails: run the ESP32's 3V3 to red + and GND to blue −; modules tap power nearby and GND is shared automatically.
  • Don't mix 5V and 3.3V on one rail: use the other rail for 5V modules (1602 LCD, HC-SR04) and label it.
  • My buttons did nothing: I'd wired two legs of the same internal pair, which are always connected. Diagonal legs fixed it (see the button section).

Electrical basics before wiring

Voltage V
The potential difference between two points, like water pressure. ESP32 HIGH = 3.3V, LOW = 0V.
Current I
How much actually flows, in mA. Too much current is what burns parts.
Resistance R
Limits current. V = I × R tells you what resistor to use for a given voltage.
Digital vs analog
Digital is just HIGH/LOW; analog is a continuous voltage turned into a number (0–4095) by the ADC.
PWM
Fast on/off switching fakes "half on": the duty ratio sets brightness or motor speed.
Pull-up / pull-down
Gives an unconnected input a defined level so it doesn't float.

This is the trap I hit most: many starter modules are designed for the 5V Arduino Uno. The ESP32 outputs and accepts 3.3V only. A module that only listens is usually fine; one that sends 5V back (HC-SR04 Echo, the 1602 backpack pull-ups) needs handling.

How pins connect to the ESP32: four styles

Read a new module's pin names and you can tell which style it uses:

Pin names look likeStyleHow to wire
IN, OUT, SIG, PLAYE, Trig, EchoGPIOAny safe GPIO, one wire per signal
SDA, SCLI2CSDA→21, SCL→22; share among devices, told apart by address
SCK/CLK, MOSI/DIN, MISO, CS, DCSPISCK→18, MOSI→23, MISO→19; one CS per device
TX, RXUARTCross over: their TX→ESP32 RX; avoid 1/3, use 16/17
VCC, VIN, GNDPower3.3V or 5V per module; GND always shared

Names can lie: the 1.8" TFT is printed SCL/SDA, which looks like I2C, but it's really SPI SCK/MOSI. The giveaway is the CS and DC pins, which only SPI has.

Module ②: 4-digit 7-segment display

Something like a 5641AS/3461AS with 12 pins. The key is the split of duties: 8 segment lines choose what shape, 4 digit lines choose which digit. Same-named segments are joined across all four digits, so only one digit can be lit at a time; fast rotation fools the eye.

Module ③: 1602 LCD + I2C backpack

A bare 1602 needs a dozen wires; the PCF8574 on the backpack turns it into I2C with just 4. This was my first "bus": more I2C devices can share SDA/SCL, told apart by address.

Module ④: 1.8" TFT color screen (SPI)

A small red board, 128×160, ST7735 driver, 3.3V logic — wires straight to the ESP32 without level shifting. Data only flows to the screen, so no MISO. I used it for a Windows 95 boot screen and a retro-Mac stock ticker.

  • Why CS on GPIO 5: it's the VSPI default CS; it is a strapping pin, but its default HIGH matches CS's idle HIGH, so no conflict.
  • DC and RST on 16/17: plain pins, not strapping pins. (On a WROVER with PSRAM, 16/17 are taken.)
  • Offset image or red/blue swapped: these boards come in black/green/red-tab variants needing different init settings. Mine is black tab.

Module ⑤: 4-leg push button

The simplest input, hiding three ideas: pull-ups (a defined level when released), the 4-leg internals (wire diagonally), and bounce (one press chatters several times). My first version used 5 buttons for up/down/left/right/OK, with all button GNDs chained and one wire to the ESP32 GND — which is correct.

Short vs long press is just timing: under 30 ms is noise, released before 3 s is a short press, held to 3 s counts as long immediately.

Module ⑥: ISD1820 record/playback module

Hold REC to record ~10 s into the chip; the ESP32 only "presses play" — the purest GPIO-output example: raise one pin briefly.

  • Power it from 3.3V: on 5V, the ESP32's 3.3V HIGH may not register as HIGH.
  • What it can't do: no programmed melodies (use a passive buzzer) and no Bluetooth audio (use an I2S module like the MAX98357A or a ready-made BT receiver board).

Module ⑦: 4×3 matrix keypad

Five buttons cost 5 pins plus GND wires; a matrix keypad does 12 keys on 7 wires, no GND and no resistors. The price is scanning: pull one column low at a time and see which row follows.

  • Row lines need pull-ups, so not 34–39 (no internal pull-up); also avoid GPIO 12.
  • Float the columns you aren't scanning so pressing two keys can't short outputs.
  • Biggest lesson: R1–R4/C1–C3 are the keypad's internal rows and columns, not the ribbon's left-to-right order. Wiring "R1…C3 left to right" made every key wrong; having the board report which two GPIOs connect let me deduce the mapping from 6 key presses, with no rewiring.

Gotcha: garbled serial output (unsolved)

Serial Monitor is set to 115200 to match the code, yet the output is still garbage, and it's unsolved. Current hypothesis: a 26 MHz crystal instead of 40 MHz shifts the real rate to 74880. Next step: try 74880 in Serial Monitor. Until then I debug by drawing state on the screen (that's how the button and keypad tests worked).
