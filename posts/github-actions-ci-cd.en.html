GitHub Actions．CI/CD for a Zero-Build Static Site

First what CI/CD actually is and why you'd want it — then this very site as the example, taking apart its actual config and check scripts to show how it gets to "every change is checked automatically, and only ships if it passes."
Source: built for this site Compiled: 2026-08-22

TL;DR

🤖 CI/CD = letting a machine do the pre-release check and the release itself. CI checks every change for breakage; CD ships it automatically once the check passes.

🧱 Even a tiny site benefits. This one has no framework and no build step, yet every post means editing five files in sync — miss one and readers never see it. Rules that rely on "remembering" are exactly what CI is good at taking over.

🚦 The one thing that matters: if the check fails, nothing ships. The first run caught several bugs that had been live for weeks without anyone noticing.

First: what is CI/CD?

Whether it's code or a website, the scary part isn't breaking something — it's breaking it without knowing, and letting readers find it first. CI/CD puts a tireless, never-forgetful robot between "done editing" and "live."

Stands forIn plain wordsAnswers
CIContinuous IntegrationEvery change triggers an automatic check"Did this change break anything?"
CDContinuous DeploymentOnce the check passes, the new version ships automatically"If it's fine, can I skip deploying by hand?"

An analogy: CI is the kitchen tasting the dish before it leaves; CD is sending it out automatically once it passes. Chain them and your only job is the cooking (editing content) — the process handles the rest.

GitHub Actions is GitHub's built-in version of that robot. You drop a config file in your repo that says "every time someone pushes, run these steps," and GitHub runs it on its own machines, showing a green ✅ or red ❌.

Why this site needs it: one post, five files

This site is deliberately simple: no framework, no build step — the files you write are the web pages. The price is that nothing tells you when you've skipped a step.

Forget the sitemap, for instance, and the page still opens, the home page still shows it — Google just never indexes it. No error, just a silent failure. These rules used to live in a README and in someone's memory; CI's job is to turn "remember to" into "checked every single time."

How this site does it: check → green → ship

The checks come in two layers, cheapest first:

CheckHowWhat it catches
① File checkReads the files as text, no browserThe five files out of sync, links to pages that don't exist, anything that breaks dark mode
② Browser checkOpens an invisible browser in the cloud and loads every page at phone widthChart text spilling out or overlapping, pages pushed wider than the phone screen, script errors

Why two layers? Some problems are visible in the file itself (a missing line); others only show up once the page is actually laid out (does this label fit its box?). Layer one finishes in a second, and if it fails there's no point spending time opening a browser.

One more setting to remember: in the repo's Settings → Pages, switch the deploy source from "branch" to "GitHub Actions." Otherwise GitHub ships the moment you push, and no red check can stop it. The essence of CD isn't "deploys automatically," it's "can refuse to deploy."

Taking it apart: the three files behind this site's CI

① ci.yml: a to-do list

A yaml file under .github/workflows/; GitHub finds it and follows it. This is the site's actual file (trimmed, permissions omitted):

on:                                  # when to run
  push: {branches: [main]}           # on a push to main
  pull_request:                      # on a pull request

jobs:
  check:                             # job 1: check (CI)
    runs-on: ubuntu-latest           # borrow a Linux machine from GitHub
    steps:
      - uses: actions/checkout@v7    # borrowed: fetch the code
      - uses: actions/setup-node@v7  # borrowed: install Node
      - run: node tools/check.mjs    # ours: file check
      - run: npm ci && npx playwright install --with-deps chromium
        working-directory: tools     # install the borrowed library + browser
      - run: node tools/visual.mjs   # ours: browser check

  deploy:                            # job 2: ship (CD)
    needs: check                     # ← only runs if check is green
    if: github.ref == 'refs/heads/main'  # PRs get checked, never shipped
    steps:
      - uses: actions/checkout@v7
      - uses: actions/upload-pages-artifact@v5   # borrowed: package the site
      - uses: actions/deploy-pages@v5            # borrowed: publish to Pages

Two keywords are all you need: uses: borrows an action someone already wrote (GitHub and the community have tens of thousands — fetching code, setting up tools, deploying are the same for every project, so nobody should write them again); run: runs your own command. A typical CI file is borrowed steps wrapped around your own checks.

② check.mjs: the checker we wrote

.mjs is just a JavaScript file using the modern import syntax; node file.mjs runs it directly, no compiling. This one uses only what Node ships with (reading files) and installs nothing. Simplified, it works in three steps:

import { readFileSync } from 'node:fs';          // built into Node: read files
const sitemap = readFileSync('sitemap.xml', 'utf8');  // ① read

for (const p of POSTS)                              // check every post
  if (!sitemap.includes(`/posts/${p.slug}.html<`))  // ② compare
    bad('sitemap.xml', `missing ${p.slug}`);       // note it, keep going

if (errs.length) { console.error(errs); process.exit(1); }  // ③ problems → red
console.log('✓ all checks passed');                      //    none → normal exit = green

The last two lines are the point: CI doesn't read what you print — it only looks at the code your program exits with. exit(1) is red; a normal exit is green. So any script in any language can plug into CI, as long as it exits non-zero when something's wrong.

The real check.mjs is about 100 lines of this same pattern repeated a dozen times: sitemap, home-page cards, zh/en pairing, category registration, hardcoded colors… each one a "remember to…" line from the README.

③ visual.mjs: borrowing someone else's library

Writing "open a browser from code and measure whether text fits" from scratch means controlling a browser yourself — tens of thousands of lines. So this uses Playwright, a browser-automation library maintained by Microsoft. Borrowing a library takes three steps:

StepOn this siteIn plain words
1. DeclareOne line in tools/package.json: "playwright": "^1.56.0"The shopping list: this package, this version
2. Installnpm ci in the CI fileDownload it from npm, the public package registry
3. Useimport { chromium } from 'playwright' at the topPut it to work

In use it looks like this — the grunt work of driving a browser goes to the library; we only write "how to tell something's wrong":

import { chromium } from 'playwright';               // the borrowed browser remote

const browser = await chromium.launch();                // start an invisible Chrome
const page = await browser.newPage({ viewport: { width: 390, height: 800 } });  // phone width
for (const f of pages) {
  await page.goto('file://' + join(ROOT, f));          // open each page
  problems.push(...await page.evaluate(probe));         // run *our* measurements inside it
}

It ends the same way, with process.exit(1) for red. And the library lives only in tools/, used only by CI — the site itself still has zero dependencies; delete tools/ and it runs just the same.

Bugs the first run caught

All of these had been live for a while and nobody noticed, because no human is going to open 80 pages one by one on a phone — a machine will.

ProblemWhat readers saw
One unescaped apostropheThe stock cards at the bottom of an English post were completely blank
Long strings that never wrapped7 pages wider than the phone screen, text cut off on the right

CI's value isn't only "it won't break in future" — it's telling you right now where it's already broken.

Three takeaways

1. CI/CD isn't just for big companies. If your project has any "remember to do X" rule, hand it to a machine.

2. Start with rules you've already written down. No need to invent tests — the "remember to…" lines in your README are the highest-return checks there are.

3. Make the check able to block the release. A check that only notifies after the fact gets ignored; red means no deploy is what makes it matter.
