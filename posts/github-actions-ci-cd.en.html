GitHub Actions．CI/CD for a Zero-Build Static Site

This site deliberately has no framework, no npm, no build step — but publishing one post means keeping five files in sync, entirely by hand. Miss one and readers silently never see it.
The fix is to turn the discipline into executable checks: one zero-dependency static pass, one that actually opens a headless browser and measures the layout. Green light or no deploy.
Source: built for this site Compiled: 2026-08-22

TL;DR

🧱 A static site needs no build, but it still needs checks. Skipping the build step removes the bundler, not the correctness guarantee. What actually breaks here is cross-file consistency — the post, both homepages, the sidebar index, and the sitemap all have to agree — and that is precisely what CI is good at.

🔍 Two layers, cheapest first. check.mjs has zero dependencies and runs in about a second: five-point sync, hardcoded colors, duplicate marker ids, dead links. visual.mjs opens headless Chromium and loads all 80 pages at 390px wide, catching SVG text that overflows or overlaps, page-level horizontal overflow, and JS exceptions — 16 seconds.

🚦 The whole point of the CD half is making deployment blockable. GitHub Pages defaults to "push to main, it ships" — a red CI ships too. Switch the Pages source to GitHub Actions and hang needs: check on the deploy job, and broken pages simply never reach production.

🐛 The first run caught four classes of real bugs. An entire inline script dead from an unescaped stock's; seven pages overflowing horizontally on mobile; two figures with overlapping labels. All had been live for weeks with no reports — because nobody scrolls 80 pages at 390px looking for it.

The problem isn't the missing build — it's the five sync points

The price of zero build is that nothing tells you when you skipped a step. In a compiled project a missing import fails the build. Here, forgetting the two sitemap lines leaves the page perfectly openable and the homepage card perfectly visible — search engines just never index it. Silent failure, discoverable only weeks later by working backwards from traffic numbers.

So the first thing worth automating isn't test logic — it's translating the rules in CLAUDE.md into asserts. The rules were already written down. They just lived in a document meant for humans.

Two layers, cheapest first

Layer 1: zero-dependency consistency

The whole thing is one file, tools/check.mjs, with nothing installed. The POSTS array is sliced straight out of site.js and eval'd — it's a file I wrote, so it doesn't need a parser:

/* POSTS in site.js is the single source of truth — just eval the array literal */
const siteJs = read('assets/site.js');
const start = siteJs.indexOf('var POSTS=[');
const end   = siteJs.indexOf('\n];', start);
const POSTS = eval(siteJs.slice(start + 'var POSTS='.length, end + 2));

After that it's rules translated into if statements one at a time. The earnings rule is the instructive one, because it's inverted:

// Earnings posts live in a data table, not the card grid; everything else needs a card
const earn = p.cat === '財報分析';
const has = idx.includes(`href="${href}"`);
if (earn && has)   bad(name, `${p.slug} is an earnings post — it must NOT have a card`);
if (!earn && !has) bad(name, `missing post-card for ${p.slug}`);

Drafts work the same way: a post with draft:1 must have homepage cards (so local preview shows them) and must not be in the sitemap. Rules of the "sometimes required, sometimes forbidden" shape are exactly the ones human memory gets backwards — once they're asserts, there's nothing left to remember.

One reverse check deserves special mention: scanning posts/ for orphan pages not registered in POSTS. The forward check only proves "everything registered exists"; it can't catch "exists but unregistered" — and that's the failure that makes a post vanish from both the sidebar and the homepage.

Layer 2: actually measure it in a browser

One class of question no regex can answer: will this line of text fit inside its box? Text width depends on the font, weight, tracking, and how CJK and ASCII interleave — only the layout engine knows. So layer two launches Chromium, loads pages over file:// (this site opens directly, so no server needed), and measures in-page:

for (const svg of document.querySelectorAll('svg')) {
  const box = svg.getBoundingClientRect();
  const rects = texts.map(t => t.getBoundingClientRect());
  // geometry escapes the canvas -> the SVG clips it, the reader never sees it
  if (r.right > box.right + 1 || r.bottom > box.bottom + 1) …
  // overlapping by more than 2px on BOTH axes -> genuinely stacked
  if (inter(rects[i], rects[j]) > 2 && vinter(rects[i], rects[j]) > 2) …
}

Using getBoundingClientRect() instead of getBBox() is the key detail: the former is in screen space and folds in any transform. The latter returns a box in the element's own coordinate system, so a single transform anywhere in the figure makes every comparison wrong.

Viewport is pinned at 390px — iPhone portrait. Desktop width almost never collides; narrow is the real stress test.

CD: making deployment blockable

GitHub Pages deploys from a branch by default. In that mode CI is a post-mortem notification: the broken page shipped long before the email arrived. To give the checks teeth, switch the Pages source to Actions (repo Settings → Pages → Source → GitHub Actions, a one-time manual change), then:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: 22}
      - run: node tools/check.mjs
      - run: npm ci && npx playwright install --with-deps chromium
        working-directory: tools
      - run: node tools/visual.mjs

  deploy:
    needs: check            # <- the only line in this file that matters
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: {path: .}
      - uses: actions/deploy-pages@v4

The if: github.ref == 'refs/heads/main' line lets PRs run checks without deploying. Splitting check and deploy into two jobs rather than two steps of one job matters because needs only expresses dependencies between jobs — and it's what renders them as two separate boxes in the Actions UI.

The one npm dependency, quarantined in tools/

This project's rule is "no build tools, no npm, no frameworks." Headless checking requires Playwright, which violates that literally — so the answer was to seal it inside tools/:

LocationContentsShips with the site?
tools/package.jsonone devDependency: playwrightNo — read only by CI
tools/node_modules~95MB of browserNo — gitignored
assets/, posts/plain HTML/CSS/JSYes, and entirely unchanged

The test is simply: is the site itself still zero-build and zero-dependency? Yes. tools/ is scaffolding for checking; delete it and the site runs exactly the same. That's a categorically different thing from pulling in webpack to build the site.

body{ … overflow-wrap:break-word; … }              /* let long runs break */
@media(max-width:640px){ table{display:block;overflow-x:auto} }  /* wide tables scroll themselves */

Worth noting: those two CSS lines exist because the checks forced them into existence. Before CI, there was no moment at which anyone would think to measure scrollWidth across 80 pages at 390px.

Two traps along the way

Trap 1: scroll-behavior:smooth silently defeats the detector

The obvious way to detect horizontal overflow is "scroll all the way right, see how far it went":

window.scrollTo(9999, 0);
return window.scrollX;   // always 0 — even though the page clearly scrolls

site.css sets html{scroll-behavior:smooth}, which makes scrolling an async animation, so the next line still reads the pre-animation 0. I briefly concluded every overflow was a false positive and reverted a CSS fix that was actually correct. What settled it was injecting a deliberately 900px-wide div and checking whether the detector noticed — it didn't, which proved the detector was broken rather than the pages being fine.

// The checker needs checking too: confirm it catches a case that MUST fail
await page.evaluate(() => document.body.insertAdjacentHTML('afterbegin',
  '<div style="width:900px;height:20px">x</div>'));

Two fixes exist: pass behavior:'instant' to skip the animation, or don't scroll at all and read document.documentElement.scrollWidth. I took the latter — it mutates no page state and removes a timing assumption.

Trap 2: getBoundingClientRect() doesn't care that you've been clipped

Every figure on this site sits inside .fig{overflow-x:auto}, so figures being wider than the viewport is deliberate — desktop fits them, mobile scrolls them inside their own box. But a naive "find elements whose right edge exceeds the viewport" flags every one of those SVGs, because getBoundingClientRect() reports the geometric rectangle whether or not an ancestor clips it.

The correct question is whether the page scrolls, not whether some element is wider than the viewport. The former excludes every overflow:auto container for free, in one line:

// .fig is overflow-x:auto — wide figures scroll themselves. Page-level overflow means something escaped.
if (document.documentElement.scrollWidth > window.innerWidth + 1)
  out.push('page overflows horizontally');

Deliberately not done

Each of these was considered; each came out as "not worth it yet":

SkippedWhyAdd it when
A second pass in dark modeText geometry and console errors are theme-independent. The one theme-dependent failure — hardcoded colors — is already blocked by the static layer, no browser requiredYou start doing screenshot diffing (visual regression)
Lighthouse / a11y scoringA plain static site scores well by default; adding it just means a few points of noise drifting on every PRYou start caring about Core Web Vitals, or get an accessibility report
An HTML validatorUncorrelated with how this site actually breaks — the bugs are cross-file inconsistency and layout overflow, not unclosed tagsYou start accepting externally-authored HTML
Caching ChromiumThe download is about 40 seconds and the whole pipeline finishes inside 90; the savings don't justify a cache action plus its invalidation problemsCI time gets long enough that you stop waiting for it
External link 404 checksSomebody else's outage turns your CI red, and re-running doesn't fix it — the textbook definition of a flaky testMoved to a weekly schedule that notifies but never blocks deploys

The shared test: when this check goes red, will I actually go fix it? Yes → add it. No, or can't → it's noise, and noise trains you to ignore red, including the red that mattered.

Under 200 lines total: no test framework, no config file, no fixtures. The checking scripts should obey the project's simplicity rules too — if the tooling gets more complicated than the thing it checks, it becomes another maintenance burden and eventually gets switched off.

The ordering is worth copying as well: start with the rules you've already written down but currently enforce by memory. That's the highest-return slice, because the thinking is already done — the only missing piece is enforcement.
