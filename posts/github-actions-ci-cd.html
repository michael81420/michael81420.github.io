GitHub Actions．幫零建置靜態站補上 CI/CD

先講 CI/CD 到底是什麼、為什麼需要,再用這個網站當實例——拆開實際的設定檔與檢查腳本,看它怎麼做到「每次改完自動檢查,沒問題才上線」。
來源:本站自建 整理日:2026-08-22

TL;DR

🤖 CI/CD = 讓機器幫你做「上線前檢查」和「上線」這兩件事。CI 負責每次改完自動檢查有沒有弄壞,CD 負責檢查過了自動上線。

🧱 再小的網站也用得上。本站沒有框架也沒有建置步驟,但每發一篇文章要同時改五個檔案,漏一個讀者就看不到——這種「靠人記得」的規則,正是 CI 最擅長接手的事。

🚦 真正的關鍵只有一個:檢查沒過,就上不了線。第一次跑就抓到好幾個已經上線很久、卻沒人發現的 bug。

先搞懂:CI/CD 是什麼?

寫程式或寫網站,最怕的不是改壞,是改壞了自己不知道,直接給讀者看到。CI/CD 就是在「改完」和「上線」中間,放一個不會累、不會忘的機器人把關。

全名白話回答的問題
CIContinuous Integration
持續整合		每次改完,機器自動跑一遍檢查「這次改動有沒有弄壞東西?」
CDContinuous Deployment
持續部署		檢查通過,機器自動把新版放上線「沒問題的話,能不能不用我手動上線?」

打個比方:CI 像餐廳出菜前的試味道,CD 像試過沒問題就自動端出去。兩個接起來,人只要負責「做菜」(改內容),剩下的交給流程。

GitHub Actions 就是 GitHub 內建的這個機器人:你在專案裡放一份設定檔,寫清楚「每次有人 push,就照這幾個步驟做」,它就會在 GitHub 的機器上自動執行,結果用綠勾 ✅ / 紅叉 ❌ 顯示出來。

本站為什麼需要?一篇文章要改五個檔案

這個站刻意做得很簡單:沒有框架、沒有建置步驟,檔案寫好直接就是網頁。代價是沒有任何東西會提醒你漏了一步。

例如漏改 sitemap:頁面照常打得開、首頁照常顯示,只是 Google 永遠收錄不到——不會報錯,只會默默失敗。這些規則原本寫在說明文件裡、靠人記得;CI 做的事,就是把「靠人記得」變成「機器每次都檢查」。

本站怎麼做:檢查 → 綠燈 → 上線

檢查分成兩層,便宜的先跑:

檢查怎麼查抓什麼問題
① 檔案檢查不開網頁,直接讀檔案內容比對五個檔案有沒有對上、有沒有連到不存在的頁面、深色模式會不會壞
② 瀏覽器檢查在雲端開一個看不見的瀏覽器,用手機寬度把每一頁真的打開圖上的字有沒有超出框或疊在一起、手機版會不會被撐寬、網頁有沒有程式錯誤

分兩層的理由很單純:有些問題看檔案就知道(漏了哪一行),有些問題一定要真的排版出來才知道(這行字到底會不會超出框)。第一層 1 秒就跑完,壞了就不必再花時間開瀏覽器。

還有一個設定要記得:到 GitHub 專案的 Settings → Pages,把部署來源從「分支」改成「GitHub Actions」。不改的話,GitHub 在你 push 的當下就直接上線,檢查再紅也擋不住。CD 的精髓不是「自動上線」,而是「有辦法不上線」。

拆開來看:本站 CI 的三個檔案

① ci.yml:一張工作清單

放在 .github/workflows/ 底下的 yaml 檔,GitHub 看到就會照著做。這是本站實際的檔案(節錄,省略權限設定):

on:                                  # 什麼時候跑
  push: {branches: [main]}           # 推到 main 時
  pull_request:                      # 有人開 PR 時

jobs:
  check:                             # 工作一:檢查(CI)
    runs-on: ubuntu-latest           # 借 GitHub 一台 Linux 機器
    steps:
      - uses: actions/checkout@v7    # 借來的:把程式碼抓下來
      - uses: actions/setup-node@v7  # 借來的:裝好 Node
      - run: node tools/check.mjs    # 自己寫的:檔案檢查
      - run: npm ci && npx playwright install --with-deps chromium
        working-directory: tools     # 安裝借來的 lib 和瀏覽器
      - run: node tools/visual.mjs   # 自己寫的:瀏覽器檢查

  deploy:                            # 工作二:上線(CD)
    needs: check                     # ← check 綠燈才輪到它
    if: github.ref == 'refs/heads/main'  # PR 只檢查,不上線
    steps:
      - uses: actions/checkout@v7
      - uses: actions/upload-pages-artifact@v5   # 借來的:打包網站
      - uses: actions/deploy-pages@v5            # 借來的:發佈到 Pages

看懂兩個關鍵字就夠了:uses: 是借別人寫好的 action(GitHub 官方和社群已經寫好幾萬個,下載程式碼、裝環境、部署這種每個專案都要做的事,都不必自己寫);run: 是跑你自己的指令。一份 CI 通常就是「借來的步驟」夾著「自己的檢查」。

② check.mjs:自己寫的檢查員

.mjs 就是 JavaScript 檔,只是用現代的 import 寫法;node 檔名 就能直接跑,不用編譯。這支只用 Node 內建的功能(讀檔),不裝任何套件。它的運作方式簡化起來就三步:

import { readFileSync } from 'node:fs';          // Node 內建:讀檔
const sitemap = readFileSync('sitemap.xml', 'utf8');  // ① 讀

for (const p of POSTS)                              // 每篇文章逐一檢查
  if (!sitemap.includes(`/posts/${p.slug}.html<`))  // ② 比對
    bad('sitemap.xml', `缺 ${p.slug}`);            // 記下問題,繼續查

if (errs.length) { console.error(errs); process.exit(1); }  // ③ 有問題 → 紅燈
console.log('✓ 全部檢查通過');                            //    沒問題 → 正常結束 = 綠燈

重點在最後兩行:CI 看不懂你印了什麼,只看程式結束時回傳的代碼。exit(1) 就是紅燈,正常結束就是綠燈。所以任何語言、任何腳本,只要「有問題就用非 0 結束」,都能接進 CI。

實際的 check.mjs 約 100 行,就是這個模式重複十幾次:sitemap、首頁卡片、中英頁對應、分類有沒有登記、有沒有寫死顏色……每一條都對應說明文件裡一條「記得要…」。

③ visual.mjs:借別人的 lib

「用程式打開瀏覽器、量字有沒有超框」如果自己寫,要從零控制一個瀏覽器,工作量是幾萬行。所以這裡直接用 Microsoft 維護的 Playwright——一個專門遙控瀏覽器的 lib。借用別人的 lib 只要三步:

步驟在本站長什麼樣白話
1. 宣告tools/package.json 寫一行 "playwright": "^1.56.0"購物清單:我要用這個、這個版本
2. 安裝CI 裡的 npm ci照清單從 npm(公開的套件倉庫)下載
3. 使用程式開頭 import { chromium } from 'playwright'拿來用

用起來長這樣——開瀏覽器、開頁面這些苦工都交給 lib,自己只寫「怎麼判斷有問題」:

import { chromium } from 'playwright';               // 借來的瀏覽器遙控器

const browser = await chromium.launch();                // 開一個看不見的 Chrome
const page = await browser.newPage({ viewport: { width: 390, height: 800 } });  // 手機寬度
for (const f of pages) {
  await page.goto('file://' + join(ROOT, f));          // 逐頁打開
  problems.push(...await page.evaluate(probe));         // 在頁面裡跑「自己寫的」量測
}

最後一樣用 process.exit(1) 回報紅燈。另外這份 lib 只放在 tools/ 裡、只給 CI 用,網站本身還是零依賴,拿掉 tools/ 網站照跑。

第一次跑就抓到的 bug

這些問題都已經上線好一陣子,沒有任何人發現,因為沒有人會用手機逐頁把 80 個頁面看一遍——但機器會。

問題讀者看到什麼
一個沒處理好的英文單引號某篇英文文章下半部的個股卡片整塊空白
太長的英文字串不換行7 個頁面在手機上整頁被撐寬,右邊的字被切掉
圖上文字疊在一起兩段字互相壓住,都讀不清楚

CI 的價值不只是「以後不會壞」,更是立刻告訴你現在已經壞在哪。

帶走三個重點

1. CI/CD 不是大公司專利。只要你的專案有「要記得做 X」的規則,就值得交給機器。

2. 從你已經寫下來的規則開始。不用先想要測什麼——說明文件裡那些「記得要…」,直接翻成檢查,投報率最高。

3. 讓檢查擋得住上線。只會事後通知的檢查,久了就會被忽略;紅燈就不能上線,檢查才真的有用。
