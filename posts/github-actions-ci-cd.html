GitHub Actions．幫零建置靜態站補上 CI/CD

這個站刻意沒有框架、沒有 npm、沒有建置步驟——但「一篇文章要同步五個地方」完全靠人工紀律,漏一處讀者就看不到。
做法是把紀律寫成可執行的檢查:一層零依賴的靜態掃描,一層真的開 headless 瀏覽器看版面,綠燈才准上線。
來源:本站自建 整理日:2026-08-22

TL;DR

🧱 靜態站不需要「建置」,但需要「檢查」。零建置省掉的是打包工具,不是正確性保證。這站真正會壞的地方是跨檔案的一致性(文章、兩份首頁、側欄清單、sitemap 要互相對得上),而那正是 CI 最擅長的事。

🔍 分兩層,便宜的先跑。check.mjs 零依賴、1 秒跑完,用讀檔加 regex 判五處同步、寫死色碼、重複 marker id、死連結;visual.mjs 開 headless Chromium 把 80 個頁面在 390px 寬各載一次,抓 SVG 文字超框/重疊、整頁橫向溢出、JS 例外——16 秒。

🚦 CD 的重點只有一件事:讓部署有辦法被擋下來。GitHub Pages 預設是「push 到 main 就上線」,CI 紅燈也照上。把 Pages 來源改成 GitHub Actions、deploy job 掛 needs: check,壞頁面才進不了線上。

🐛 第一次跑就抓到四類真 bug:一支 inline script 因為 stock's 沒跳脫整個掛掉、6 個頁面在手機上橫向溢出、2 張圖的文字疊在一起。這些都上線好一陣子了,沒人回報,因為沒人會用 390px 逐頁看 80 個頁面。

問題不是「沒建置」,是「五處同步」

零建置的代價是:沒有任何東西會告訴你漏了一步。編譯型專案漏了 import 會編不過,這裡漏了 sitemap 兩行,頁面照常打得開、首頁卡片照常顯示,只是搜尋引擎永遠收不到——靜默失敗,而且要幾週後才會從流量數字反推出來。

所以第一個要自動化的不是測試邏輯,是把 CLAUDE.md 裡的規則翻譯成 assert。規則本來就寫好了,只是寫在給人看的文件裡。

兩層檢查:便宜的先跑

第一層:零依賴的靜態一致性

整支就一個檔案 tools/check.mjs,不裝任何套件。POSTS 陣列直接從 site.js 切出來 eval——那是自己寫的檔案,不需要寫 parser:

/* site.js 的 POSTS 是全站唯一事實來源,直接把陣列字面值 eval 出來 */
const siteJs = read('assets/site.js');
const start = siteJs.indexOf('var POSTS=[');
const end   = siteJs.indexOf('\n];', start);
const POSTS = eval(siteJs.slice(start + 'var POSTS='.length, end + 2));

接著就是把規則一條一條寫成 if。財報分析那條最有代表性——它是反過來的規則:

// 財報分析走資料表,不進 #grid;其餘兩份 index 各要一張卡
const earn = p.cat === '財報分析';
const has = idx.includes(`href="${href}"`);
if (earn && !has)  bad(name, `${p.slug} 是財報分析,不該有首頁卡片`);
if (!earn && !has) bad(name, `缺 ${p.slug} 的 post-card`);

草稿同理:draft:1 的文章必須有首頁卡片(本機預覽要看得到)、但必須不在 sitemap。這種「有時候該有、有時候該沒有」的規則,人腦最容易記錯,寫成 assert 之後就再也不用記。

還有一條反向檢查值得特別提:掃 posts/ 底下有沒有沒登記進 POSTS 的孤兒頁。正向檢查只能保證「登記的都存在」,抓不到「存在但沒登記」——後者會讓文章從側欄和首頁整個消失。

第二層:真的開瀏覽器量一次

有一類問題無論如何 regex 都判不出來:這行字到底會不會超出框。字寬取決於字型、字重、字距、CJK 與 ASCII 混排——只有排版引擎知道。所以第二層直接開 Chromium,用 file:// 載頁(這站本來就能直接開,不用起 server),在頁面裡量:

for (const svg of document.querySelectorAll('svg')) {
  const box = svg.getBoundingClientRect();
  const rects = texts.map(t => t.getBoundingClientRect());
  // 文字的幾何矩形跑出畫布 → 被 SVG 裁掉,讀者看不到
  if (r.right > box.right + 1 || r.bottom > box.bottom + 1) …
  // 兩段文字在水平與垂直都重疊超過 2px → 真的疊在一起
  if (inter(rects[i], rects[j]) > 2 && vinter(rects[i], rects[j]) > 2) …
}

用 getBoundingClientRect() 而不是 getBBox() 是關鍵:前者是螢幕座標,自動把 transform 算進去;後者回傳的是元素自己座標系裡的框,只要圖上有任何 transform,比對就會錯。

視窗寬度固定 390px(iPhone 直式)。桌機寬度幾乎不會撞版,窄版才是真正的壓力測試。

CD:讓部署有辦法被擋下來

GitHub Pages 預設從分支部署。這個模式下 CI 只是事後通知:壞頁面早就上線了,信件才寄到。要讓檢查真的有牙齒,得把 Pages 來源換成 Actions(repo Settings → Pages → Source 選 GitHub Actions,手動切一次),然後:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: {node-version: 22}
      - run: node tools/check.mjs
      - run: npm ci && npx playwright install --with-deps chromium
        working-directory: tools
      - run: node tools/visual.mjs

  deploy:
    needs: check            # ← 整份 yaml 只有這行是重點
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: {path: .}
      - uses: actions/deploy-pages@v4

if: github.ref == 'refs/heads/main' 讓 PR 只跑檢查、不部署。check 跟 deploy 拆成兩個 job 而不是同一個 job 的兩個 step,是因為只有 job 之間才能用 needs 表達依賴,也才會在 Actions 頁面上顯示成兩個獨立的方塊。

唯一一份 npm 依賴,關在 tools/ 裡

這站的規矩是「不要加建置工具、npm、框架」。headless 檢查需要 Playwright,直接違反字面規則——所以做法是把它整個關進 tools/:

位置內容會不會進到網站
tools/package.json一個 devDependency: playwright不會,只有 CI 讀
tools/node_modules約 95MB 的瀏覽器不會,已加進 .gitignore
assets/、posts/純 HTML/CSS/JS會,而且完全沒變

判準是:網站本身還是零建置、零依賴嗎? 是。tools/ 是檢查用的鷹架,拿掉它站台照跑。這跟「為了做網站而引入 webpack」是完全不同的兩件事。

第一次跑就抓到的四類問題

CI 的價值不是「以後不會壞」,是它立刻告訴你現在已經壞在哪。這四類全部是已經上線一段時間、沒有人回報的問題:

問題影響為什麼沒被發現
未跳脫的單引號
the stock's fundamentals 寫在單引號字串裡		EP689 英文頁整支 inline script SyntaxError,個股卡片與族群表完全沒 render頁面上半部完全正常,只有下半段空白;不開 console 看不出來
長字串不換行
Alphabet/Amazon/Meta/…、TSM/NVDA/MU/…		7 個頁面在 390px 寬整頁橫向溢出,右側文字被推出畫面外桌機完全看不到;手機上要往右滑才會發現字被切掉
SVG 文字重疊
EP689 圖表標題壓到資料標籤、Oracle 英文版數字壓到註解		兩段字疊在一起,都變得難讀重疊只有幾 px,掃過去像是「有點擠」而不像 bug
寬表格不捲
表格 min-content 寬度超過視窗		同樣造成手機橫向溢出同上,而且是全站共通問題,不屬於任何一篇

修法有兩種層級。單引號跟 SVG 座標是逐篇修;另外兩個是全站共通,兩行 CSS 一次解決:

body{ … overflow-wrap:break-word; … }              /* 長字串該斷就斷 */
@media(max-width:640px){ table{display:block;overflow-x:auto} }  /* 寬表格自己捲,不推寬整頁 */

值得注意的是:這兩行 CSS 是被檢查逼出來的。在有 CI 之前,沒有任何一刻會讓人想到要去量 80 個頁面在 390px 下的 scrollWidth。

踩到的兩個坑

坑一:scroll-behavior:smooth 讓偵測整個失效

最直覺的橫向溢出偵測是「捲到最右邊,看捲了多少」:

window.scrollTo(9999, 0);
return window.scrollX;   // 永遠是 0 —— 但頁面明明會捲

原因是 site.css 有 html{scroll-behavior:smooth},捲動變成非同步動畫,下一行讀到的還是動畫開始前的 0。我一度因此以為所有溢出都是誤判、還把已經修好的 CSS 又還原回去。實測驗證的方法是故意塞一個 900px 的 div 進去,看偵測器抓不抓得到——抓不到,才確定是偵測器壞了不是頁面沒問題。

// 檢查器自己也要被檢查:先確認它抓得到「一定有問題」的情況
await page.evaluate(() => document.body.insertAdjacentHTML('afterbegin',
  '<div style="width:900px;height:20px">x</div>'));

解法有兩個:傳 behavior:'instant' 繞過動畫,或者根本不要捲——直接讀 document.documentElement.scrollWidth。最後用了後者,不改動頁面狀態、也少一個時序假設。

坑二:getBoundingClientRect() 不管有沒有被裁切

這站的圖都包在 .fig{overflow-x:auto} 裡,圖比視窗寬是刻意的設計(桌機自適應、手機在圖框內橫向捲)。但如果直接找「右邊界超出視窗的元素」,這些 SVG 全部會被抓成溢出——因為 getBoundingClientRect() 回報的是幾何矩形,不管它實際上有沒有被祖先容器裁掉。

正確的判準是問「整個頁面會不會捲」,而不是「有沒有元素比視窗寬」。前者自動把所有 overflow:auto 容器排除掉,一行搞定:

// .fig 有 overflow-x:auto,圖再寬也該自己捲;整頁橫向溢出才代表有東西沒包好
if (document.documentElement.scrollWidth > window.innerWidth + 1)
  out.push('整頁橫向溢出');

刻意沒做的事

每一項都想過,結論都是「現在加不划算」:

沒做理由什麼時候該加
light / dark 各跑一輪文字幾何與 console 錯誤都跟主題無關;唯一跟主題有關的失敗是寫死色碼,已經被靜態層擋掉了——不需要開瀏覽器驗證開始用截圖比對(視覺回歸)的時候
Lighthouse / a11y 分數純靜態站分數本來就高,加了只是每次 PR 多幾個上下 1 分的雜訊開始在意 Core Web Vitals 或收到無障礙回報時
HTML validator跟真實壞掉的方式沒有關聯——這站的 bug 是跨檔案不一致與版面溢出,不是標籤沒閉合開始接受外部投稿 HTML 的時候
快取 Chromium下載約 40 秒,整條 pipeline 一分半內跑完;省下來的時間不值得多一個 cache action 的設定與失效問題CI 時間開始讓人不想等的時候
外部連結 404 檢查會因為別人的網站掛掉而讓自己的 CI 變紅,還不能重跑解決——這是最典型的不穩定測試改成每週排程跑、只發通知不擋部署

共通的判準是:這個檢查紅燈的時候,我會不會真的去修? 會 → 加。不會或修不了 → 它只是噪音,而噪音會讓人開始忽略所有紅燈,連真的問題一起忽略。

檔案行數做什麼

總共不到 200 行,沒有測試框架、沒有設定檔、沒有 fixture。檢查腳本本身也該符合專案的簡單原則——如果檢查工具比被檢查的東西還複雜,遲早會變成另一個要維護的負擔,然後被停用。

順序也建議照這個來:先把你已經寫在文件裡、但只靠人腦執行的規則翻成程式碼。那是投報率最高的一段,因為規則早就想清楚了,只差沒人強制執行。
