pstack．Engineering Workflows with Evidence

Source review and creator interview: verification tools, deterministic CLIs, coordinator agents, and the limits of the 2,500-PR claim.
Checked：2026-11-03 Updated: 2026-11-05 Draft

TL;DR

pstack writes engineering practices into skills an agent can read: inspect the code, choose a playbook, settle data and interfaces, implement, then verify with runtime evidence. The entry point is /poteto-mode. Architecture, parallel exploration, and adversarial review enter when needed.

My assessment: its strongest contribution is a definition of done that demands observable behavior and evidence. Projects with tests and reproducible environments benefit most. A small copy edit rarely needs a full multi-agent workflow.

The interview adds the adoption mechanism: give agents tools to observe their work, encode repeatable operations in code, and connect external reports to coordinated tasks. The reported PR volume is a personal account that includes maintenance, not a measured feature-throughput benchmark.

Try the examples：Test a fix · Recheck a combination · Connect reports

1. What the repository controls

This article combines a repository review with the creator’s interview. It examines cursor/plugins/pstack, an engineering workflow package maintained by poteto. It contains mostly Markdown instructions, agent definitions, and supporting materials. The host supplies models, tools, permissions, and sub-agent capabilities.

Installing a skill does not guarantee correct execution. Results depend on instruction following, runnable project checks, and access to the right code and tools. The sections below separate source descriptions from engineering judgments. I did not measure development speed, token cost, or defect rates.

This structure makes work rules inspectable and lets teams adopt a single skill. Maintainers must keep instructions, platform adapters, and actual tool capabilities aligned. Longer rule sets also increase the need to check execution rather than accept a narrated checklist.

3. Four methods worth understanding

architect settles interfaces and data first

Understand the existing system, compare structurally different designs, and specify types, signatures, and module ownership before filling in implementation. This fits changes across module boundaries. Repeated exceptions during implementation can signal a flawed premise.

arena compares isolated candidates

Define a rubric, create independent candidates, and have a judge compare them. Pick a base, bring in selected strengths from other candidates, then verify the combined artifact. Passing candidate tests does not establish that the combined result works.

interrogate requires a reproducible finding

Adversarial reviewers try to produce executable failure cases. The parent reruns evidence and deduplicates root causes. Upstream defines this skill as reporting findings rather than fixing them in the same step. That separates review from modification.

Verification skills preserve how to exercise a product

Create a project-specific skill that records how to start, operate, and check the application. A maintenance workflow checks whether those instructions still match the product after changes. This helps catch behavior that compilation misses, such as an unresponsive button.

4. Start with one reproducible bug

The README gives this Cursor installation entry point. Configure available models and a reasoning budget before assigning a task with clear acceptance criteria.

/add-plugin pstack
/setup-pstack
/poteto-mode

A first task might use this prompt:

On mobile, clearing the search input does not restore the article list. Reproduce it first. Determine whether input events or state updates cause it, then make the smallest fix. Verify clearing, no results, and category changes. Report the checks you ran and the conditions you did not cover.

Review the reproduction, final diff, and actual interaction results. If parallel exploration adds no useful decision evidence, let one agent finish. This adoption approach is my recommendation, not a guaranteed upstream outcome.

Claude Code uses separate installation commands:

/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins

The mode is named /pstack:poteto-mode there. Consult the adapter for Cursor-specific capabilities. This article does not infer installation commands for other hosts, and I did not run these installations.

5. Preserve what each failure teaches

My strongest reason to adopt pstack is this loop: turn a discovered mistake into structure, types, lint, or a test so that the same mistake fails automatically next time. A reminder still depends on the agent remembering. Upstream /correct explicitly works through enforcement options for recurring mistakes.

For example, a bilingual site receives a Chinese article without an English counterpart. Fixing it means adding the missing page and making the consistency check reject either missing language. This is an engineering example for this article, not a built-in pstack site feature.

Tests have limits. If they omit mobile, network failures, or data races, green checks cover only the tested conditions. Different models can also share blind spots. Agreement does not replace execution evidence.

6. Interview: how trust develops, and what engineers still own

Lauren describes becoming the human intermediary between an agent and Chrome DevTools. She inspected flame graphs and heap snapshots, then relayed findings. An agent could change code, but observation and evaluation still depended on her. Giving the agent tools to operate the application and collect traces and snapshots created a feedback process it could repeat.

She connects that feedback process to hill climbing: repeated attempts need a target and a way to score progress. The upstream hillclimb playbook specifies one change, one measurement, then keep or revert. The interview shows no measured improvement. Without a trustworthy measurement, a longer run does not establish progress.

This explains her trust ladder: establish trustworthy behavior within a limited scope, confirm that the agent can detect failures, then expand delegation and parallel work. When the host asks whether domain expertise is becoming less useful, she argues the opposite. As models become more capable, expressing intent clearly and judging whether results make sense become more valuable.

The host also uses terms such as TDD and tautological tests to explain how precise language compresses intent. Both speakers criticize tests that merely restate implementation rather than independently check behavior. My reading is that test counts alone do not establish trust: checks must be capable of failing when behavior breaks.

Her Michelin kitchen analogy emphasizes designing the workspace, tools, responsibilities, and quality process while retaining responsibility for the outcome. My interpretation is that part of engineering work moves toward a reusable, observable, constrained environment. Accountability stays with the people running it. This is an experience-based account, not a controlled production study.

7. Put repeatable operations in a CLI, and leave judgment to the agent

One concrete example explains why she built a verification CLI. Early agents kept writing fresh interaction scripts. A successful tool from one session was discarded, so the next agent rebuilt it differently. Moving shared operations into a reusable tool gave every agent the same entry point.

WorkApproach in the interviewReason
JudgmentLet the agent interpret intent, form hypotheses, and choose designsThe work requires context and decisions
Deterministic operationsUse a CLI, script, or codemodAvoid repeated generation and debugging
Product verificationDrive the application and collect observable evidenceGive the agent results it can act on

She describes the CLI as glue around Playwright, the Chrome DevTools Protocol, and other APIs. The useful property is repeatable operation. She extends the idea to migrations: a codemod can mechanically traverse and transform an AST, while an agent decides the scope and handles exceptions.

Context usage was an early motivation, but avoiding repeated work became a broader benefit. Deterministic operations move out of temporary reasoning; accepting the result still requires judgment. The interview provides no measurements of time or token savings from this CLI.

8. Dune: constrain recurring mistakes in the environment

Lauren describes Dune as a private internal framework, roughly an internal Next.js for Electron applications. In her account, early Grokbot versions had about eight enormous files of at least ten thousand lines each. Feature directories, discovery and registration conventions, and restrictive lint rules helped replace that structure.

The distinction is between documenting a preference and enforcing it. If structure and checks determine where a feature belongs and how it registers, agents have fewer choices to invent and fewer opportunities to keep expanding a giant file. She connects this to TypeScript narrowing: reduce the possible states so that incorrect choices fail.

This article cannot inspect Dune or verify those historical file sizes. The transferable method is to observe recurring agent mistakes and constrain them through structure, types, or lint. This static site can apply that principle through bilingual file conventions and consistency checks without adopting another framework.

9. Connect outside context to execution, with room to group problems

Lauren uses outer loop for information arriving through Slack, Linear, email, or X, and inner loop for reading code, implementing, and verifying against the current intent. Those are her terms in this interview. Without updated external information, the initial task can become stale.

She describes Grokbot routines collecting that context and sending it to a coordinator in Cursor Projects. The coordinator manages and delegates, while worker agents execute tasks. This describes her configuration. Installing pstack does not by itself supply those connectors, subscriptions, or cloud environments.

Why not spawn a separate fixer for every report? Multiple performance complaints may share a root cause. One report can suggest a local defect, while the combined set points to a higher-level issue. A coordinator needs shared context and deduplication, not merely more concurrent workers.

A useful detail is her routine for finding problematic React patterns. The agent records findings in a document before fixing them. Every few days, she looks for recurring patterns. That buffer lets a person or agent decide whether a single structural fix is better than many isolated patches.

The outer loop shapes the task; the inner loop returns a fix and evidence.

10. What the 2,500-PR claim does and does not establish

The host cites Lauren's earlier presentation about roughly 2,500 PRs in a month, and she also describes that volume in the first person. She explicitly says it does not mean 2,500 features. Much of the work is code maintenance and improvements to the development environment. She says she did not manually start 2,500 chats: projects, external triggers, and coordinators kept work moving.

This is a speaker's account, not a PR ledger or company-wide productivity statistic audited for this article. The transcript supplies no per-PR size, precise reporting month, defect rate, rollback rate, or complete cost. The title's SpaceX wording and the organizational names used in the conversation are attributed to the interview. They do not independently establish corporate status or company-wide results.

Verification plus sampling, rather than blocking every PR

Her account of high autonomy uses multiple verifier agents per PR to operate the product, seek regressions, fix problems, and repeat verification before merging. She acknowledges that this consumes substantial tokens and says the number of verifiers can be reduced. She describes some changes merging while she sleeps, followed by review of commit history and possible reversions or new rules the next day.

Sampling remains rigorous. If several agents take the same shortcut, she adjusts the environment and checks rather than correcting just one output. She explicitly says reaching this point takes time and effort. Installing pstack does not automatically establish that trust.

The interview offers no universal answer for irreversible changes

The host asks about changes that could destroy data, and about domains such as medicine, law, and finance where verification is difficult. Lauren says verifiability matters and acknowledges that she does not have a complete answer. Formal verification and languages combining programs with proofs appear as possible directions, not demonstrated solutions to those cases.

My engineering assessment: proving a property does not make data deletion reversible. Reverting code does not necessarily restore external state. This account is insufficient justification for unrestricted automatic merging.

11. Build your own skills from actual corrections

The closing discussion asks whether different skill libraries can work together. Lauren recommends examining past conversations for repeated interventions, corrections, and missing context, then turning effective practices into rules, tools, or skills. A transcript shows how a process actually unfolded rather than how its author remembers an ideal process.

She uses /recall as an example. Work on virtualization repeatedly needed findings from earlier chats, so she captured the process of finding past context and reconstructing current state. She also argues that stronger models can make some overly detailed instructions unnecessary, leaving skills more focused on workflow.

This is consistent with the CLI approach: tools retain repeatable operations, while a skill explains when to use them and how results affect the next decision. Combining libraries still requires resolving conflicts in responsibilities, steps, and permissions. I would establish one working path for a real task before adding another skill.

12. Costs and adoption limits

  • Parallel candidates, judges, and parent verification all consume context and model usage. No cost benchmark was run for this article, so it claims no savings or speedup.
  • Isolation reduces conflicting edits, but someone must integrate the result. Shared files, test environments, and external state limit parallel work.
  • Skills instruct models. Host permissions and project policy must still constrain publishing, merging, deletion, and external tool actions.
  • Platform support needs adaptation. The Claude Code adapter can fall back to the session model, so a review may lose model diversity. The repository documents a generated Claude Code distribution and an adapter; that does not establish parity with every Cursor capability.

I would use it for projects with CI, executable checks, and repeated complex changes. For a small static content edit, one agent and existing checks usually require less coordination. These are judgments based on the workflow design, not measured comparisons.
