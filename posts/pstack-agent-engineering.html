pstack．讓 AI 寫程式有流程，也有驗證

從原始碼與作者訪談拆解 pstack：驗證工具、確定性 CLI、協調 agent、內外迴圈，以及每月 2,500 個 PR 自述的意義與限制。
整理／查核日：2026-11-03 更新：2026-11-05 草稿

TL;DR

pstack 把資深工程師的工作方式寫成 agent 可讀的 skills：先讀程式、選工作劇本、釐清資料與介面，再實作並拿執行結果回來驗證。入口是 /poteto-mode，需要時才呼叫架構設計、平行探索與對抗審查。

我的判斷：它最有價值的地方，是把「完成」定義成可檢查的行為與證據。已有測試、可重現環境的專案最能受益；簡單改字或沒有驗證路徑的專案，不必套上整套多 agent 流程。

訪談進一步說明採用過程：讓 agent 自己觀察結果，把固定操作寫成工具，將外部回報接進協調流程。每月 PR 數量是包含維護工作的個人自述，不能當成已驗證的功能產能。

互動練習：比較修正證據 · 重驗整合版本 · 合併回報脈絡

一、讀這個 repo 時，先看它控制什麼

本文結合 repo 原始碼閱讀與作者訪談，分析使用者提供的 cursor/plugins/pstack。它是由 poteto 維護的工程工作流套件，內容主要是 Markdown 指令、agent 定義與輔助材料。它依賴宿主提供模型、工具、權限與子 agent 能力。

因此，裝好 skill 並不代表多了一個保證正確的執行引擎。宿主模型是否遵守指令、專案能否跑測試、不同工具能不能取得同一份程式，仍會影響結果。以下依原始檔說明設計，再分開提出工程判斷；未實測開發速度、token 成本或缺陷率。

二、從入口到驗證：每層負責不同的事

位置責任閱讀重點
skills/poteto-mode/選工作劇本、協調後續步驟先判斷這是 bug、功能、調查或其他工作
playbooks/依任務排列步驟修 bug 要重現；效能工作要有基準
個別 SKILL.md執行架構、探索、審查等方法需要時載入，不必每次全跑
agents/描述專門角色與任務角色能做什麼仍受宿主工具限制

這種拆法讓團隊能檢查、修改工作規則，也能只採用一項 skill。代價是維護者要同步指令、平台轉接與實際工具能力。規則越多，越需要確認 agent 真的有執行，而不是只在回覆中列出步驟。

三、值得理解的四個方法

architect：先確定呼叫方式與資料形狀

先理解現有系統，再比較結構上不同的設計，把型別、函式簽名與模組責任具體寫出來，接著才填實作。適合跨模組的功能。若每新增一步都要補例外，應回頭檢查設計前提。

arena：同題多案，最後仍要整合與重驗

先訂評選標準，讓候選方案隔離產生，再由評審比較。選定一個基底後，只移入其他方案有價值的部分，最後驗證合成結果。候選案各自通過測試，不代表合併後也通過。

  • 通過窄螢幕上的按鈕文字可讀
  • 通過Escape 只關閉一次
  • 通過關閉後焦點回到開啟按鈕
  • 未檢查實體觸控裝置

interrogate：審查意見必須能重現

不同審查者嘗試找出可執行的失敗案例，主 agent 再重跑、按根因去重。上游把這個 skill 定義為回報問題，不在同一步自行修正。這讓審查與修改的責任更清楚。

verification skills：把操作產品的方法留下來

建立專案自己的驗證 skill，把如何啟動、操作與判定結果寫成可重用流程。產品改了，再用維護流程核對舊指引是否仍符合現況。這對「編譯過了，但按鈕沒反應」這類問題有幫助。

四、實際採用：先用一個可重現的 bug

README 的 Cursor 安裝入口如下。先設定可用模型與推理預算，再把有清楚成功條件的任務交給模式。

/add-plugin pstack
/setup-pstack
/poteto-mode

例如，拿搜尋功能當第一個任務，提供這樣的需求：

手機上輸入搜尋字再清空，文章列表沒有還原。先重現，確認是輸入事件還是狀態更新的問題，再做最小修正。驗證清空、無結果與分類切換都正常。回報實際執行的檢查與未覆蓋範圍。

驗收時要看重現步驟、最終 diff 與實際操作結果。若平行探索沒有降低決策不確定性，就讓單一 agent 完成。這是本文建議的採用方式，並非上游保證的結果。

Claude Code 使用另一組安裝命令：

/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins

該平台的模式名稱是 /pstack:poteto-mode；Cursor 專屬功能需依轉接文件處理。本文不推導其他宿主的安裝命令，也沒有執行上述安裝。

五、品質來自能否把錯誤留下來

我認為 pstack 最值得採用的是這個循環：找到錯誤之後，把規則放進結構、型別、lint 或測試，讓下次相同錯誤自動失敗。只補一段提醒文字，仍仰賴 agent 每次記得。上游 /correct 就明確依可行層級處理反覆出現的問題。

例子：站內文章要有中英文兩頁，新增文章卻只建中文頁。有效的修正包含補上英文頁，並讓一致性檢查在缺任一語言頁時報錯。這個例子是本文的工程示意，不是 pstack 內建的網站功能。

可重現的測試也有邊界。若測試漏掉手機、網路失敗或資料競態，綠燈只能說明已覆蓋的條件通過。多個模型也可能共享盲點，因此多數同意不能取代執行證據。

六、訪談補充：信任怎麼建立，工程師還要做什麼

Lauren 的起點是自己成了 agent 與 Chrome DevTools 之間的人工中介。她讀 flame graph、heap snapshot，再把發現轉述給 agent；即使 AI 能改程式，觀察結果與判斷是否有效仍卡在人身上。第一個關鍵進展，是讓 agent 自己操作產品、收集 traces 與 snapshots，形成能反覆嘗試的回饋流程。

她也把這個回饋流程連到 hill climbing：先有明確目標與評分方式，才能讓 agent 反覆嘗試改善。對照上游 hillclimb 劇本，做法是一次改動、一次量測，再決定保留或回復；影片本身沒有展示量化改善結果。缺少可信量測時，執行再久也不能證明有進展。

這就是她說的 trust ladder。先讓一個 agent 在有限範圍內交出可信結果，確認它能自行發現失敗，再逐步擴大委派與平行工作。主持人問領域知識是否因此變得不重要，她的回答相反：模型更有能力之後，清楚表達目標、辨識結果是否合理的能力更有價值。

主持人另以 TDD、tautological tests 等詞說明，精準語言可以濃縮工作要求。兩人對只重述實作、無法獨立判定行為的測試都持批評態度。本文的解讀是：測試數量本身不足以建立信任，測試要有能力在行為出錯時失敗。

她用「米其林廚房」形容這件事。負責人要設計工作區、工具、分工與出餐品質，也仍對最後結果負責。本文的解讀是：工程師的工作有一部分轉向建立可觀察、可約束、能重複使用的環境；不是把責任一起交給 agent。這是講者的經驗與比喻，不是經過對照實驗證明的生產模型。

七、CLI 的作用：固定操作交給程式，判斷交給 agent

訪談裡最具體的一段，是她為何替驗證做 CLI。早期 agent 每次驗證都重新寫操作腳本；上一個 agent 做成功的工具沒有留下，下一個又重新建一次，而且做法不一致。她把共同操作收進工具，讓每個 agent 使用同一套入口。

工作性質影片的做法為什麼
需要判斷交給 agent 理解意圖、提出假設、選擇設計這些工作需要綜合脈絡，不能只靠固定命令
可確定執行的操作寫成 CLI、script 或 codemod不用每次重新生成與除錯，結果也較一致
驗證產品用工具驅動應用、觀察狀態與收集證據讓 agent 能依結果調整，而非只宣稱完成

她描述的 CLI 主要串接 Playwright、Chrome DevTools Protocol 與其他 API；重點是可重用的操作能力。她也把這個原則延伸到遷移：規律性的語法轉換可以由 codemod 走訪 AST 完成，agent 負責判斷轉換範圍與例外。

她最初也考量上下文用量，後來更重視避免重複工作。這裡的重點是把確定性操作移出臨時推理；對結果該不該接受，仍需要 agent 與人做判斷。影片沒有給出 CLI 節省多少時間或 token 的量測，本文不替它估算。

八、Dune 案例：把常見錯法擋在環境裡

Lauren 自述團隊有一個未開源的內部框架 Dune，形容它像 Electron 應用使用的內部 Next.js。她提到早期 Grokbot 有大約八個巨大檔案，每個達上萬行，之後改成每個 feature 有自己的目錄，再配合功能發現與註冊機制，以及限制較嚴格的 lint 規則。

這個案例補足「寫好規則」與「環境能強制」的差別。把程式放哪裡、怎麼登記功能若已由結構與檢查決定，agent 就少一項自由選擇，也較難繼續往既有巨型檔案塞程式。她用 TypeScript 的型別收窄解釋相同想法：縮小可能狀態，讓錯誤選項無法通過。

本文不能檢視 Dune 的實作，也沒有驗證那些歷史檔案的大小。可帶走的是一個方法：觀察多個 agent 重複犯的錯，再選擇結構、型別或 lint 來限制它。對這個靜態站而言，沿用雙語檔案規則與一致性檢查就能應用同一原則，不需要為此導入新框架。

九、外圈接脈絡，內圈寫程式；中間要能合併問題

Lauren 把外部資訊與程式開發分成 outer loop 與 inner loop。這是她在訪談中的用法：外圈從 Slack、Linear、郵件或 X 取得回報與需求；內圈根據目前目標讀程式、修改與驗證。只給 agent 最初那份需求，後續新資訊就可能進不來，目標也會過時。

她描述以 Grokbot routines 收集外部脈絡，再送到 Cursor Projects 的協調 agent。協調者以管理與委派為主，讓工作 agent 執行各項任務。這是她描述的工作配置，不能理解成安裝 pstack 就自動取得所有連接器、訂閱與雲端執行環境。

為什麼不能每來一則回報就開一個 agent 修？她舉的情境是多個效能問題可能有共同根因。單看一則會以為是局部 bug，把相關回報放在一起，才看得出更上層的問題。協調者要能共享脈絡、避免重工，不能只增加平行數量。

另一個細節更值得保留：她有 agent 持續找 React 的問題模式，先把發現追加到文件，沒有立刻要求修掉。她每隔幾天查看，辨識哪些其實是同一件事。這種暫存與彙整讓人或 agent 能先找模式，再決定一次根因修正是否比許多零碎修補更好。

十、每月 2,500 個 PR，要怎麼讀這個數字

主持人引用 Lauren 先前的分享，詢問單月約 2,500 個 PR 如何做到；Lauren 在對談中也以第一人稱描述這個數量。她隨即釐清，這不代表 2,500 個功能，很多是整理程式、改善環境等維護工作。她也說自己沒有手動建立 2,500 個對話，而是讓多個專案、外部觸發與協調 agent 持續推進。

這是講者自述，不是本文查過的 PR 清單或公司生產力統計。逐字內容沒有提供每個 PR 的大小、精確統計月份、缺陷率、回滾率或完整成本。標題中的 SpaceX 與對談裡的組織稱呼也只作影片脈絡，不據此推論公司級成果，或獨立確認其組織狀態。

從逐筆擋住，改成驗證加抽樣回看

她描述的高自主模式會對 PR 啟動多個 verifier agents，實際操作產品、尋找回歸、修正後再驗證，達到要求才合併。她坦言這很消耗 token，也可以減少驗證 agent 數量。她自述有些程式會在睡覺時合併，隔天再抽查 commit history、回滾或補上規則。

她強調仍要嚴格抽樣審查程式。若多個 agent 都走同一種捷徑，就調整環境與檢查，而不只糾正那一次輸出。她也明說，走到這一步要投入很多時間與心力，裝 pstack 並不會自動建立這份信任。

不可逆變更，影片沒有給出通用解答

主持人追問可能造成資料損失、難以回復的變更，以及醫療、法律、金融等難驗證情境。Lauren 承認領域是否可驗證很重要，也沒有完整答案。她談到形式驗證與結合程式、證明的語言作為可能方向，沒有展示足以解決這些情境的驗證成果。

本文的工程判斷是：證明某項性質成立，不能自動讓資料刪除變得可逆；能回滾程式，也不等於能恢復已改掉的外部狀態。這段經驗不能直接當成全面放開自動合併的理由。

十一、技能怎麼變成自己的：從真實糾正紀錄開始

對談最後，兩人談到不同技能庫能否混用。Lauren 建議回看自己的聊天紀錄，找出反覆介入、重複糾正與需要補脈絡的地方，再把有效工作方式變成規則、工具或 skill。實際紀錄能看出流程如何發生，比憑印象寫一份理想規範更具體。

她以 /recall 為例：處理虛擬化相關問題時，新對話常需要前一次的發現，於是把查閱歷史脈絡、重建目前狀態的做法收成技能。她也認為模型能力提升後，有些過細的操作提示可以刪掉，讓 skill 更集中在工作流程。

這與前面的 CLI 並不衝突。可重用的操作保留在工具裡；skill 說明何時使用、依什麼結果決定下一步。混用技能時要處理責任、步驟與權限的衝突，本文建議先把一個真實任務的流程跑通，再加入下一項技能。

十二、採用前要算的成本與風險

  • 平行候選、評審與主 agent 重驗都消耗上下文與模型用量。本文沒有成本實測，不宣稱更便宜或更快。
  • 隔離工作能減少互相覆寫，但最後仍需要負責整合的人。共享檔案、測試環境與外部狀態會限制平行效率。
  • skills 是給模型的指令。發佈、合併、刪除與對外工具操作，仍需由宿主權限及專案政策限制。
  • 跨平台支援需要轉接。Claude Code 轉接可能回退到對話使用的模型，因此不一定保留跨模型審查的多樣性。原始碼中有 Claude Code 產生版與轉接說明，不能直接假設所有 Cursor 功能都在其他宿主存在。

適合已有 CI、可執行測試、需要反覆處理複雜變更的專案。只有少量靜態內容修改時，用單一 agent 加既有檢查通常更省事。這些是依工作流結構提出的判斷，沒有量化比較。

十三、互補工具怎麼選

工具補上什麼何時用
Playwright實際操作瀏覽器並斷言 UI 行為網站需要可重跑的操作證據時
TLA+ / TLC對狀態模型檢查不變量與反例併發、重試與狀態轉換難靠案例覆蓋時

兩者都不能代替 pstack 的任務協調；pstack 也不能代替它們實際執行驗證。TLC 的結論針對寫下來的模型，模型是否忠實描述產品仍要另查。
